# 11/27 导航：起点贴墙被拒 + 车后箱子导致永久停车

记录时间：2026-11-27
涉及代码：`pi/nav2_patch/`、`pi/ros2_lidar/tools/motion_scan.py`、
`pi/ros2_lidar/tools/scan_motion_gate.py`、`pi/carhealth/`
相关提交：`4da3149`、`cd641b1`、`181adaf`

这次实车“导航失败”其实是两个独立问题叠在一起：

1. **起点（或终点）足迹靠近墙/近物时，Smac 直接 `Start occupied`**，
   即使车只是侧边贴进墙外 0.20 m 的保守带。
2. **车后放了一个箱子，collision_monitor 永远 `STOPPED`**，
   即使导航方向是往前——门控把箱子漏在了输出里。

---

## 一、起点贴墙被拒（`Start occupied`，error 205）

### 现象

- 车停在墙边或起点附近有近物，`NavigateToPose` / `ComputePathToPose`
  直接失败，错误码 205 `Start occupied`。
- 之前实测：起点距墙 0.10/0.20/0.30/0.40 m 都 ABORTED，0.50 m 才成功。
- 用户判断：车能停在那里就是物理事实；只要不是“没数据/没 TF”，
  起点应该一律放行。若代价图说压墙，优先怀疑地图/定位。

### 关键测量：253 到底是什么

在 fusion 栈的全局代价图上，从原点沿垂直于最近致命格的方向逐格打印
`/global_costmap/costmap_raw`：

| 距原点 | cost | 含义 |
|---|---|---|
| 0.00~0.15 m | 171→230 | 正常膨胀衰减 |
| **0.20~0.35 m** | **253** | inscribed 环，墙外 0.20 m |
| **0.40~0.45 m** | **254** | 墙本身（地图画了 2 格 = 0.10 m 厚） |
| 0.50~0.65 m | 253 | 墙另一侧同样的 0.20 m 环 |
| 0.70 m+ | 230→0 | 衰减到自由 |

结论：**253 = 墙两侧各 0.20 m，正好等于 `inscribed_radius=0.20`，
不是物理墙**。车侧边（离中心 0.20 m）一旦贴进这个带，旧逻辑就拒绝。

### 根因

`nav2_smac_planner/src/collision_checker.cpp` 的 `inCollision`：

```cpp
if (center_cost_ == INSCRIBED || center_cost_ == OCCUPIED) {
  return true;   // 中心落在 253 环里就直接判无效
}
```

只要“中心”在墙外 0.20 m 内，就跳到“碰撞”，连足迹都不检查。
起点和所有邻居都在环里 → A* 只迭代 1 次 →
`SmacPlannerHybrid` 抛 `StartOccupied`。

### 修复：最小补丁，不用 `forceValid`

补丁在 `pi/nav2_patch/nav2_overlay.patch`，只改两处：

1. `nav2_smac_planner`：判据从 `>=253` 收紧到 `>=254`（`LETHAL`）。
   中心在 253 时**继续做足迹检查**（原有 `footprint_cost >= OCCUPIED` 分支），
   只有足迹真的压到致命格才判无效。
2. `nav2_regulated_pure_pursuit_controller`：只跳过**当前位姿**那一次碰撞
   否决（位姿是物理事实）；路径前方的投射检查保留，避免
   “planner 放行、controller 却 Collision Ahead”。

副作用：goal 走同一个 `isNodeValid`，也一起放宽；已在 `NAV.md` 明示。
`reverse_penalty` / `cost_penalty` / `analytic_expansion_max_cost` 未动。

### 构建与部署（容易踩的坑）

- 源码必须是 jazzy 分支（补丁基准 `94d1c2a3`），只编两个包：
  `nav2_smac_planner`、`nav2_regulated_pure_pursuit_controller`。
- 不要编测试：Pi 上 smac 的测试目标非常慢，用 `-DBUILD_TESTING=OFF`。
- **三处**都要在 `/opt/ros/jazzy/setup.bash` 之后 source overlay：
  `nav.service`、`slam.service`、`upper/run.sh`。
- `carhealthd` 新增 `nav2_overlay` 组件：跑
  `ros2 pkg prefix nav2_smac_planner`，必须指向 `~/nav2_ws/install`；
  没编/没 source 时 DEGRADED。
- 验证运行中的进程确实加载 overlay（比看源码可靠）：

```bash
pid=$(pgrep -f nav2_planner/planner_server | head -1)
grep -o '/home/cy/nav2_ws[^ ]*\.so' /proc/$pid/maps
```

### 验收（只规划不动车）

工具：`pi/ros2_lidar/tools/start_clearance_probe.py`
（在代价图里找一段竖直致命墙，把车平行放在墙边，发
`ComputePathToPose`，`use_start: true`）。

实测（nav_20261124，墙格 (0.49, 1.15)，车头 +y）：

```
side 0.10 m  center=232 body_edge=253 -> SUCCEEDED error=0
side 0.20 m  center=190 body_edge=253 -> SUCCEEDED error=0
side 0.30 m  center=156 body_edge=232 -> SUCCEEDED error=0
body 0.05 m inside wall  center=253 body_edge=254 -> ABORTED error=205
```

即：侧边落在 253 环里都放行；足迹真压 254 时，起点和所有邻居都无效，
仍然 `StartOccupied`（符合验收表）。

## 二、车后箱子导致 collision_monitor 永久停车

### 现象

- 用户把车倒到距箱子很近的位置（车尾轮胎离箱子 3.5 cm、保险杠 7 cm），
  再点导航，车完全不动。
- 不是 planner 的问题：同一时刻 `ComputePathToPose` 从当前位姿
  `(0,0)` 到 `(1,0)` 两次都 `SUCCEEDED`。
- `collision_monitor` 日志反复出现：

```
Robot to stop due to invalid source...
Robot to stop due to stop_zone polygon
Latest source and current collision monitor node timestamps differ on 0.625 s
```

### 排查过程

1. 先量 `/scan_motion_guard` 在 stop_zone（0.90×0.56 m）里的点：
   248 个点，全部集中在车后。
2. 第一次算成了“车中心后方 0.12 m、横跨全宽”，误判为自车结构。
   **教训：`/scan_motion_guard` 的 header frame 是 `laser`，不是
   `base_footprint`；必须用 TF 变换后再判断。**
3. 用 `base_footprint <- laser` 的 TF 重算：箱子在 base 坐标
   `x=-0.36~-0.38`、`y=-0.22~0.20`，与卷尺（3.5/7 cm）吻合。
4. 查雷达参数：`range_min=0.150`。箱子的回波范围是
   **0.117~0.149 m，全部低于 `range_min`**。
5. 查 `motion_scan.filter_ranges_union`：

```python
if not math.isfinite(r) or r < range_min or r > range_max:
    continue     # 跳过但“不置 inf”，点原样留在输出里
```

低于 `range_min` 的点被跳过、原样保留，所以：
**不管前进还是后退，箱子永远在 `scan_motion_guard` 里。**

### 为什么后果是“永久停车”

- `collision_monitor` 的 `stop_zone` 覆盖车后 0.45 m，箱子在区内；
- 停车时 `cmd=0`，门控按设计不过滤（fail-open），箱子留在输出；
- CM 进入 `STOPPED`，`cmd_vel_nav` 清零；
- 控制器再发前进指令，门控**本应**按前进走廊把箱子滤掉，但因为
  `range_min` 跳过逻辑，箱子一直在 → CM 继续 STOP；
- BT 进度检查超时 → 导航失败。

### 修复

`pi/ros2_lidar/tools/motion_scan.py`：只跳过非有限、非正、超 `range_max`
的点；低于 `range_min` 的真实回波也按走廊几何处理。

```diff
- if not math.isfinite(r) or r < range_min or r > range_max:
+ if not math.isfinite(r) or r <= 0.0 or r > range_max:
```

`range_min` 仍保留在函数签名里（调用方兼容），但不再用于跳过点。
新增两个测试：

- `test_near_return_below_range_min_is_still_filtered`：
  0.12 m 的后方回波（base -0.376）必须被前进走廊过滤；
  先确认旧代码会红（`checked=0`）再修。
- 更新 `test_filter_ranges_only_skips_nonfinite_samples`：
  明确“低于 range_min 的有限回波按走廊处理”的新契约。

全部 `pi/ros2_lidar/tests`：92 passed。

### 验证（同一帧实车雷达数据，离线跑门控）

| 指令 | stop_zone 剩余点 |
|---|---|
| 前进 0.25 m/s | **0** |
| 前进 + 转 0.3 rad/s | **0** |
| 原地转 0.3 rad/s | 2 |
| 倒车 0.1 m/s | 248 |

结论：前进放行；倒车/原地转仍会停——**物理上正确**，箱子离车尾只有
3.5 cm，倒车或原地转本来就会碰。修复后用户实测导航恢复正常。

部署：`git pull` → `deploy_nav.sh`（同步 `tools/`）→
`systemctl restart scan-gate`。门控是 systemd 服务，不需要重编 ROS。

## 三、经验

1. **代价图的 253 不是墙**，是 `inscribed_radius` 的膨胀环；判断“是不是
   真压墙”要看 254，并且要看**足迹**而不是中心。
2. **“起点一律放行”不等于“永远不报 Start occupied”**：Smac 不校验起点
   节点本身，只校验邻居；如果起点和邻居都真压 254，仍会只迭代 1 次。
3. **雷达坐标 ≠ base 坐标**：`/scan_*` 的 frame 是 `laser`（车后方
   0.256 m），任何“距离车中心”的判断必须先做 TF。这次差点把真实箱子
   误判成自车点。
4. **`range_min` 不是“无效数据”的同义词**：近距离真实障碍的回波会低于
   传感器标称最小值，过滤层不能把它们当作无效值原样放过。
5. **过滤器的契约要用测试锁死，并且先让测试红**：这次两个 bug 都能用
   纯几何单测复现，不需要实车。
6. **验证“补丁是否生效”看进程加载的 .so**（`/proc/<pid>/maps`），
   比看源码/看服务文件可靠。
