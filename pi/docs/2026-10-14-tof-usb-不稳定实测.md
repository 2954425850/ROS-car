# ToF(USB) 掉线 + Pi5 掉压 · 真机实测记录

> 2026-10-14。起因：ToF 模块的 LCD 看着"卡死不动"，怀疑模块在反复挂掉。
> 结论：**不是我们的代码。是两个独立的问题叠在一起。** 其中 Pi 掉压这条会
> **连带把机械臂串口也打掉**，直接威胁抓取闭环。

---

## 摘要（先看这个）

| # | 现象 | 频率 | 与"我们"的关系 |
|---|---|---|---|
| 1 | **Pi5 报 `Undervoltage detected`** | 35 分钟 **11 次** | 与我们无关；但会打掉 USB 设备 |
| 2 | **机械臂串口掉线** | 2 次，各在掉压后 ~2s | 同一个根因，**会毁掉抓取** |
| 3 | **ToF 模块重新枚举** | 今天 5 次 | 与掉压**不相关**；关 LCD **没治好** |
| 4 | `ttyUSB` 编号会变 | 每次重枚举 | 写死 `/dev/ttyUSB0` 必炸 |

---

## 证据 1：Pi 5 真的在掉压（这是新问题，不是我们引入的）

```
hwmon hwmon3: Undervoltage detected!   ← 开机 15:42 起共 11 次
15:55:35 15:55:48 15:56:00 15:56:06 15:56:14   ← 一分钟内连着 5 次
15:56:26 15:56:35 15:57:16 16:03:37 16:12:27 16:16:17
```

**电源协商数据（关键）**：

```
/sys/firmware/devicetree/base/chosen/power/max_current              = 0x00001388 = 5000 mA
/sys/firmware/devicetree/base/chosen/power/usbpd_power_data_objects = 28 字节**全 0**
/boot/firmware/config.txt:  usb_max_current_enable=1
```

⇒ **没有发生 USB-PD 协商**（PDO 全零）。树莓派只是被 `usb_max_current_enable=1`
**强制告知"你有 5A"**，于是它按 5A 放行 USB 电流 —— 但**供电端实际能不能给出 5V
它一无所知，系统也不会为此做任何保护**。

⚠️ 所以"驱动板额定 5V/5A"这句话**不能推出"Pi 输入端有 5V"**：
掉压是 Pi 的 PMIC 在**它自己输入端**测的，线材长度/线径、接插件接触电阻、
驱动板走线压降都会先吃掉一部分。**额定够 ≠ 到手够。**

## 证据 2：机械臂串口跟着一起掉（这条最要命）

```
15:57:13  l150pro_driver: 底盘故障位 0x10（链路超时）
15:57:14  usb 4-1: USB disconnect          ← 1a86:55d4 = 机械臂串口(serial ...1357)
15:57:14  l150pro: 串口断开（读失败: device reports readiness to read but returned no data）
15:57:14  l150pro: 串口打开失败: No such file or directory: '/dev/l150pro'
15:57:16  hwmon hwmon3: Undervoltage detected!      ← 2 秒后掉压
15:57:19  l150pro: 串口已打开 /dev/l150pro
```

`16:03:36 disconnect → 16:03:37 undervoltage` 是同一模式。

⇒ **掉压和机械臂串口掉线是同一件事的两面。** 抓取跑一半遇到这个，
`/arm/feedback` 会断流，`grasp.run` 的行为不可预期。

## 证据 3：LCD 背光**不是**模块掉线的原因（否定结果）

先把 `A010.LCD` 关掉（`DISP` 3→2，只留 USB 位）做对照，节点也确认在用 `DISP=2`
（帧率 **9.6 → 22.8 fps**，见下）。**结果模块照样掉**：

| 时刻 | 当时 DISP | 前后 30s 内有掉压吗 |
|---|---|---|
| 15:51:57 | 3 | 无 |
| 15:53:56 | 3 | 无 |
| **16:16:39** | **2（LCD 已关）** | 有（16:16:17），但隔了 22s |
| **16:19:09** | 2 | **无** |
| 16:21:03 | 2 | 无 |

⇒ 5 次模块掉线里 **4 次前后没有掉压**。**LCD 背光洗清了**，模块重枚举另有原因。
（顺带：`DISP=2` 把帧率翻倍是个额外收获，可以考虑直接采用。）

## 证据 4：`ttyUSB` 编号会变（这条直接坑到我们）

同一次重枚举后通道号会平移：

| | 重枚举前 | 重枚举后 |
|---|---|---|
| 通道 A（数据口, `1.0`） | `ttyUSB0` | **`ttyUSB1`** |
| 通道 B（`1.1`） | `ttyUSB1` | **`ttyUSB2`** |

实测：16:19 那次之后 `/dev/ttyUSB0` **直接不存在了**。
⇒ 任何写死 `/dev/ttyUSB0` 的脚本都会在重枚举后失效
（我们那个临时 A/B 探针就是这么崩的）。
**`code 里走 `/dev/serial/by-id/...-if00-port0` 是对的**（语义=通道 A，
数字怎么变都跟得住），`config.resolve_device` 已按这个兜底。

## 证据 5：已排除的嫌疑

| 嫌疑 | 结论 |
|---|---|
| ModemManager 抢占串口 | ❌ 排除。它**跟着设备出现**才反应（都在出现后 4~6s），且明确报 `not supported by any plugin`，没开这两个口 |
| USB 过流保护 | ❌ 排除。`over-current / device not accepting / error -71` 计数**全为 0** |
| LCD 背光 | ❌ 排除（证据 3） |
| 我们的代码 | ❌ 不背锅。模块在**没有任何代码跑的时候**（12:28，20 秒内 3 次）就在掉 |

## 附带发现：`DISP=2` 帧率翻倍

| DISP | 位 | 实测帧率 |
|---|---|---|
| 3 | LCD(1)\|USB(2) | **9.6 fps** |
| 2 | USB(2) | **22.8 fps** |

LCD 开着时模块的渲染管线要分一份力给屏 ⇒ 掉一半。**抓取不需要 LCD**
（深度走 USB），所以 `disp_mode: 2` 不但省电、还让深度更新鲜一倍。

> ⚠️ 但这给供电实验带来一个**混淆**：帧率翻倍 ⇒ 模块自己耗电可能也上去了。
> 若要干净地比较背光，得先把两边都用 `AT+FPS` 钉在同一帧率。

## 需要做的（按优先级）

1. **查供电电压（必须，软件无解）**：万用表量**Pi 输入端**的 5V，
   分别在**空载**和**加载**（机械臂动起来 / K230 + ToF 都开）时各量一次。
   掉压说明负载下压降过大 ⇒ 换粗短线、换接插件、或给外设上**独立带供电的 USB HUB**。
2. **模块掉线的物理 A/B**（还没做）：同一个模块换 **另一根线**、换 **另一个 USB 口**
   （直插 vs 经过那个 Genesys HUB），各跑 10 分钟数重枚举次数。
   → 能把"线/口"和"模块板子本身"分开。
3. **软件加固（我可以做）**：装 udev 规则 `99-tof-a010.rules`
   —— 给出稳定名 `/dev/a010`，并给 FT2232 加 `ID_MM_DEVICE_IGNORE`
   （机械臂那条规则当初就是这么治 ModemManager 的）。
4. **降低总线负载**：无线手柄占 **350mA**、K230 占 **500mA**，抓取时用不上手柄。
   声明总和 90+100+136+350+500 = 1176mA，Pi5 上限 1600mA —— 余量不多，
   而 **A010 的真实电流根本没申报**（它只说 90mA，板子自己却要 5V/0.5A）。

## 本文件里"没证明"的部分（诚实标注）

- 模块 5 次重枚举的**具体原因未确定**。已知它**不**由掉压、LCD、ModemManager 引起。
  剩下的嫌疑是：线材/接插件、USB 端口、或模块板子自身的固件看门狗 —— 都需要动手换件才能分。
- 我**没能量到实际电压数值**：Pi5 的 `rpi_volt` hwmon 只暴露报警位
  （`in0_lcrit_alarm`），没有 mV 读数；`rp1_adc` 的 4 路没有 label，读数还在飘，
  不能当 5V 轨用。

# 第二轮（当晚）· 三个新的软件坑（都已修）

模块恢复后把链路跑通了，期间踩到三个**会让"模块坏了"这个误判成立**的坑：

## 坑 1：串口默认**不独占**，两个进程能同时打开

Linux 默认允许多个进程开同一个 tty。于是第二个 opener **open() 成功**，
直到读的时候才炸：

```
SerialException: device reports readiness to read but returned no data
  (device disconnected or multiple access on port?)
```

★ 这个报错**极具误导性** —— 它读起来像"设备掉了/模块死了"，实际是"两个进程在抢"。
**实测踩过**：`tof_node` 在跑的时候又去跑 `tof_probe`，就是这条。

**修**：`A010.open()` 用 `exclusive=True`（TIOCEXCL）。
之后第二个 opener 立刻拿到干净的锁失败
（注意 errno 是 **11 EAGAIN**，不是 16 EBUSY），`tof_probe` 会打人话提示先停节点。

## 坑 2：开串口**不会**把 DISP 复位 ⇒ 应答被帧数据淹

DISP 掉电不保存（上电回 1），但**开串口/DTR 并不复位它**。
所以上次留的 `DISP=2/3` 会让模块一直推流。这时 `AT+xxx?` 的应答里混着帧数据，
而 `cmd()` 会在**帧的 payload 里碰巧找到 `OK` 三个字节** ⇒
返回 `ok=True` 但正文是乱码：

```
AT+BAUD?  ok=True  b'@BBBCDEFGGGFEEEMWONem[OOQSSSTTV[v\xa1\xff\xff...'
```

**修**：`tof_probe` 查询前先 `AT+DISP=0` 停流。修完应答干净：
`+BAUD=2` / `+UNIT= 4` / `+BINN=1` / `+DISP=0`。

## 坑 3：重连猛敲 = 把模块按住反复复位

原来的重连是 1s 一敲 ⇒ 每 ~3s 开一次串口 ⇒ **每 3 秒复位模块一次**，
模块永远等不到缓过来的机会（实测连敲 39 次都没成功）。
**修**：指数退避 1→2→4→…→20s。

另：设备压根不在总线上时**只等、不开**（不刷 "No such file" 噪声）。

## 顺带确认的行为

- **`DISP=2`（LCD 灭）帧率是 `DISP=3` 的两倍多**：9.6 → **26 fps**。
  抓取不需要 LCD（深度走 USB），所以 `disp_mode: 2` 直接定下来。
- 通道号（`if00` → ttyUSB0/1）**会随重枚举平移**。已确认 by-id 是稳的，
  并且**每次重连都重新解析路径**，不用打开时的快照。
- `/tof/status` 里已加 `port` 字段（by-id 实际落到的 ttyUSB），
  出问题时第一眼看的就是它。
