## 1. 背景与动机

2026-09-17 的 `2026-09-17-car-tools-design.md` 已经暴露一个结构性问题：

> 唤醒模块的串口监听和整条对话流水线**共用一个线程** —— 见 `wakeword/engine.py`
> 的 `_listen_loop → _handle_detection`，它是**内联**调回调的。

当时小车是靠「每个工具都别阻塞、立刻返回」绕过去的（`move_distance` / `turn_by`
改成起后台线程）。**但那个绕法只对「不需要返回值」的工具成立。**

现在要加「拍照 + 云端视觉理解」：模型**必须拿到画面内容才能回答**，没法 fire-and-forget。
而实测延迟是 **4~10 秒**（§4.4）。所以绕不过去了，只能动握手本身。

### 实测证据（三条，都已核对代码）

1. `wakeword/engine.py` `_handle_detection()` 内联调 `self._on_detected()`；
   `start()` 的 Args 注释还把这写成「**这正是我们想要的**：整条对话流水线跑完之前
   不会被重复触发」—— 也就是说，**阻塞是故意的**，它同时兼职防重入。
2. 回调返回后有 `_drain()` 调 `reset_input_buffer()` **清空串口缓冲**。
   所以盲窗里按下的唤醒帧是**被丢掉**的，不是排队等 —— 用户得在盲窗结束后**重新喊一次**。
   这比「延迟响应」更糟，也是本次要修掉的东西。
3. `core/conversation.py` 模块 docstring：「整条流水线是**同步串行**的……这是本项目
   刻意的设计，**改动时请勿破坏**」。本文正是要**有据地**改掉它的一半 —— 见 §3.3，
   「串行」这条不变量**保住了**，被换掉的只是「跑在哪个线程上」。

### 1.1 B 修的是哪一段盲窗（先说清楚，别把它说过头）

**车在动、音乐在放的时候喊唤醒词，一直是有效的** —— 而且那两件事跟本文无关：

- 运动跑在 `CarController` 自己的 `car-motion` 线程上，工具是 fire-and-forget、**立刻返回**；
- 音乐跑在 `MusicController` 自己的线程上，`start_pending()` 是在**进 IDLE 之后**才调的。

两种情况下**流水线早已返回**，监听线程是空闲的，所以唤醒词进得来。
09-17 实车踩的「他在往前走的时候，喊他没用」是**另一个** bug ——
`move_distance` 当时写成了阻塞式，当天已改成 fire-and-forget。
**那个事故不能拿来当 B 的理由。**

**B 真正修的是「流水线自己忙」那一段**：LISTENING / THINKING / SPEAKING。
其中会咬人的是这两个：

| 场景 | 盲窗长度 | 改动前 |
|---|---|---|
| **SPEAKING**（TTS 正在说话，车在动） | 几秒 | 喊不动车 |
| **THINKING 里正跑着工具** | `look` 来了就是 **4~10 秒** | 车能白走 1~3 米 |

所以准确的说法是：**B 主要是为 `look` 铺路的**（它的结果模型必须拿到，
没法像运动那样 fire-and-forget），顺带补上 TTS 那段盲区 ——
不是在修一个已经修过的问题。

## 2. 目标与非目标

**目标**

- 串口监听线程**永远只做读串口**，任何长度的操作都不再阻塞它。
- 「喊唤醒词 = 急停」在**任何**时刻可用，包括流水线正忙（拍照中、TTS 中、放歌中）时。
- 新增工具 `look(question)`：K230 拍照 → 云端视觉模型 → 返回画面内容。

**明确不在范围**

- **TTS 打断**（喊唤醒词打断正在说的话）—— 今天也没有这个能力，本文不引入，见 §7 坑 3。
- **延迟播报机制**（工具后台跑完再回灌一句话）—— 选了 B 就不需要。
- **读板端 KPU 结果**（`k230ctl result`）—— 用户 2026-09-18 明确说后续做。
- 任何对 `mcp_host/` 的改动。

## 3. 核心设计：把「唤醒」拆成快慢两段

### 3.1 契约反转

`WakeWordEngine.start(on_detected=...)` 的回调契约**反过来**：

| | 今天 | 改后 |
|---|---|---|
| 回调要求 | 同步跑完整条流水线 | **必须立刻返回**（<400ms） |
| 防重入 | 隐含在「不返回就不读串口」里 | **显式**，由调用方负责 |
| `_drain()` | 清掉流水线期间堆积的帧 | **保留**（此时只堆了 stop 的 ~320ms，语义仍对） |

**引擎几乎不用改代码** —— 它本来就只是「读字节 → 调回调」。要改的是它的 **docstring**：
`start()` 的 Args 里那句「这正是我们想要的」现在是**错的**，必须重写；
`_handle_detection` 里 `finally: _drain()` 的注释也要跟着改（它现在解释的是
「回调里同步跑完了整条流水线」）。

### 3.2 快慢分离

```
_listen_loop（监听线程，永远只做这个）
  └─ _handle_detection(cmd)
       ├─ 冷却期判断（2s，不变）
       ├─ on_detected()                ← 现在必须 <400ms
       └─ _drain()

ConversationManager._on_wake_word()    【监听线程，只做快的】
  ├─ self._music.stop()                # 不变
  ├─ self._car.stop_all()              # 不变，8 帧 × 40ms ≈ 320ms
  ├─ 更新 _last_activity / 闲置判断 → 交给 pipeline 做
  └─ if 流水线空闲: 起 pipeline 线程
      else:         只做急停，不起第二条流水线（记日志）

ConversationManager._run_pipeline()    【新线程，慢的全在这】
  ├─ 闲置检查 / 可能 reset 历史
  ├─ 播唤醒提示音 + sleep(0.5)          # 从 _on_wake_word 搬过来
  ├─ transition(LISTENING) → 录音 → THINKING → … → SPEAKING → IDLE
  └─ finally: 清 busy 标志
```

**关键收益**：`_on_wake_word` 的**前两行**（两个 stop）留在监听线程上，
所以「喊了就停」这条路径的**延迟一点没变**（仍是几十~320ms），
而它现在**在流水线忙的时候也可用**（改动前那一段是盲窗，见 §1.1）。

用户第二次喊唤醒词 → 走同一条快路径 → 再停一次（幂等），
且因为 busy 标志**不会**起第二条流水线。

### 3.3 保住了的不变量：状态机仍然单线程驱动

**busy 标志保证同一时刻只有一条流水线。** `_on_enter_*` 全部回调都跑在
**同一个** pipeline 线程上，彼此不会并发。

所以 car-tools-design 里那条「同步串行」不变量**没有被破坏** ——
被换掉的只是它**跑在哪个线程上**。

**这正是选 B 而不是 C（fire-and-forget）的理由**：C 会让流水线之外的代码去写状态机，
那才是真的破坏串行。B 只是把整条串行链搬家。

### 3.4 新引入的并发面（已逐条核对）

监听线程现在会在 pipeline 线程正跑着的时候调 `music.stop()` / `car.stop_all()`：

| 调用 | 线程安全 | 依据 |
|---|---|---|
| `MusicController.stop()` | ✅ | `tools/music.py` 有 `_state_lock` 保护全部状态变更 |
| `CarController.stop_all()` | ✅ | 只发 ROS 帧；`_bridge` 懒建有 `_bridge_lock` |
| `Speaker.write()` | ✅ | `audio/speaker.py` 有 `_write_lock`，docstring 明写「并发写入方会被串行化」 |

`stop_all()` **不碰 Speaker**，所以与 pipeline 的 TTS 写音频流不会相撞。

### 3.5 `shutdown()` 的改动

现在 `_wakeword.stop()` 会 join 监听线程。加了 pipeline 线程之后，
`shutdown()` 必须**先**停/join pipeline 线程，**再**停唤醒线程 ——
否则监听线程可能正在起新 pipeline。顺序写进实现计划。

## 4. `look` 工具

### 4.1 为什么做成 tool

按 car-tools-design 已定的那条线：**意图 → 工具，原语 → 不是工具**。
`k230ctl snap` 是**原语**；「看一眼那是什么」是**意图**。

「该不该看一眼」只有模型能判断（用户说「前面有什么」要拍，「现在几点」不要拍），
而这个「何时使用」按 `prompt-no-capability-emphasis` **只能**写在 tool description 里
—— **不动 `system_prompt`**。

工具名取**意图级**的 `look`，不是 `take_photo`。

### 4.2 接口

```
look(question: str) -> str
    question: 想问画面里的什么。把用户的原话传进来最好。
```

### 4.3 云端实测（2026-09-18 在 Pi 上实跑，非文档推断）

| 项 | 结果 |
|---|---|
| 模型 | **`deepseek-flash`**（`deepseek-v4-flash-vision-exp` 是它的别名，两个 ID 真身相同） |
| 识别质量 | 真实照片 → 「一个红黄相间的**苹果**放在白色的窗台或桌沿上」 |
| 延迟 | **1.1~1.6 s**（57 KB JPEG，1280×720） |
| 图片成本 | `detail=low` 下一张 720p ≈ **180 tokens**（prompt 共 229） |
| ⚠️ 隐藏属性 | **它是推理模型**：先吐 `reasoning_content` 再吐 `content`。`max_tokens=200` 时**正文是空的** |

**结论：`max_tokens` 必须 ≥1000**（本设计取 1500）。这是最容易踩的坑 ——
表现是「工具返回空字符串」，看着像工具坏了，其实是预算被 reasoning 吃光。

复用 `llm.api_key` / `llm.base_url`（同一个 DeepSeek 账号，零新增凭据）。

### 4.4 延迟构成（这就是 §3 必须做的原因）

```
snap   3~8 s   ← 瓶颈：等 RTSP 攒够一个 GOP
                （取决于板子有没有视频接收端：有 ≈30fps / 无 ≈8.4fps）
VLM    1.1~1.6 s
────────────
总计   4~10 s
```

**云端那一跳不是瓶颈。** 省它没意义；要提速只能动 K230 侧（不在本文范围）。
所以「4~10 秒的盲窗」这件事，只能靠 §3 的握手重构解决。

### 4.5 失败面

`ToolRegistry.dispatch()` 保证不抛异常，所以每条失败路径都返回**一句人话**
让模型自己兜底：

| 失败 | 返回给模型 |
|---|---|
| `snap` 退出码非 0 | 「没拍成 —— {stderr 首行}」（`snap` 自带 3 次重试） |
| `snap` 超时 | 「拍照超时了，可能是 K230 没连上」 |
| 文件不存在 / 0 字节 | 同上 |
| API 错误 / 超时 | 「看失败了 —— {原因}」 |
| 正文为空（reasoning 吃光预算） | 「没看清」（并把 `max_tokens` 不足记进日志） |

## 7. 已知坑 / 有意不做的

1. **`_drain()` 仍会吃掉「盲窗期间」的帧。** 改后盲窗只剩 stop 的 ~320ms，
   危害基本消失；但**不改成「排队处理」** —— 那会让一次唤醒结束后被旧帧立刻再触发一次
   （引擎原注释担心的正是这个）。**丢帧是对的。**

2. **闲置判断（`session_reset_idle_sec`）搬到了 pipeline 线程。**
   它读写的 `_last_activity` 只有 pipeline 线程和 `_on_enter_speaking` 碰，
   两者现在是同一个线程 —— 反而比改动前更干净。

3. **不引入 TTS 打断。** 用户喊唤醒词时如果 TTS 正在说，今天的行为是
   「等这段话说完才进 LISTENING」（因为都在一个线程里串着）。改后 pipeline 在另一个
   线程，`_on_wake_word` 会并发跑 —— **TTS 仍然不会被中断**（没人去打断它），
   行为与今天**一致**。真正的打断要另做一个「喊唤醒词 → 掐掉 Speaker」，
   本文不做，避免把两件事混在一起。

4. **冷却期 2s 不改。** 流水线可能跑 10s，用户中途喊急停（>2s）能正常进来。
   <2s 的连喊被冷却吃掉 —— 无所谓，第一次已经停过了。

## 9. 可恢复的打断（2026-09-18 实车后追加 —— **本节作废 §7 坑 3**）

### 9.1 起因：第一次实车验证

用户让助手「说 100 个字的常对话」，助手念了 130 字 / **28 秒**。用户在它说话期间
**连喊 5 次唤醒词**，日志：

```
09:36:57  TTS: synthesizing 130 chars
09:37:04  WakeWord: detected (cmd=0x01)
09:37:04  对话流水线正忙，本次唤醒只做急停      ← B 生效了
09:37:07  WakeWord: detected
09:37:10  WakeWord: detected
09:37:13  WakeWord: detected
09:37:17  WakeWord: detected
09:37:25  TTS: complete                        ← 28 秒后才停嘴
```

**B 本身是对的**：改动前这 5 次唤醒一次都不可能被听见（串口没人读 + `_drain()` 丢帧）。
但用户体感是「我喊了五次，它理都不理我」—— 因为 B 只做了急停 + 记日志，
**没有打断 TTS**，而 §7 坑 3 把「TTS 打断」明确列成了非目标。

**结论：§7 坑 3 作废。打断是需求，不是可选项。**
（另：当时主会话交给用户的验收标准是「日志出现『正忙，只做急停』」——
那条标准达成了，但达成的结果是用户不会接受的。**验收标准要给「用户听到什么」，不是「日志里出现什么」。**）

### 9.2 用户 2026-09-18 定的通用原则

> 一般会**继续**（除了电机跑方面的），除非中间说的是「停下，不听了」这种话才会停下，
> 其余继续完成。

写成不变量：

```
打断的默认语义 = 暂停（可恢复），不是销毁

  音乐在放       → 暂停，记住位置 → 这一轮结束后续播
  TTS 在说       → 停止，放弃剩余  → 转 LISTENING（这就是"打断"本身）
  小车在动       → 急停，且【不续】 → 唯一的例外
  未来的一切能力  → 默认"继续完成"，除非用户明说停

只有用户【明说】「停下 / 不听了 / 别放了」这类 → 才真正终止（销毁暂停位）
```

**为什么运动是例外**：让车「续上刚才没走完的那两米」是危险的 —— 用户停下它是为了
说话，不是让它等会儿接着开。**这是安全要求，不是偏好。** 新增任何能力时，
若它涉及**物理位移**，都该走这条例外；纯粹的信息/媒体类能力走默认可恢复。

### 9.3 为什么音乐「暂停」而说话「放弃」

| | 性质 | 语义 |
|---|---|---|
| 音乐 | **背景内容** | 插一句话再接着听 —— 天经地义 |
| 正在说的那句话 | **前台对话** | 把半句话拼起来重新念很怪；用户想听可以再问 |

### 9.4 实现要点

**`MusicController`**
- 新增 `pause()` / `resume()`，与 `stop()` 三分：
  - `pause()`：置停止标志 + join，**但保留 `url` / `label` / 已播位置**
  - `resume()`：重新 `av.open(url)` + `container.seek(...)` 到记录的位置
  - `stop()`：**销毁性**，连暂停位一起清（语义 = 真的不听了）
- 位置记录：解码循环里记 **输入帧的 PTS**（`frame.pts * stream.time_base`），
  不要用重采样后的样本数 —— 后者和扬声器缓冲对不齐
- ⚠️ **`seek` 是按关键帧定位的**，会回到最近的一个音频关键帧，最多差几百毫秒。
  听感是「接上了，但少了一两个词」，**不是无缝续播**。本设计接受这个偏差。

**`ConversationManager`**
- `_wake_fast_action()`：`music.stop()` → **`music.pause()`**；`car.stop_all()` 不变；
  若流水线正忙 → `self._interrupt.set()`
- `_run_pipeline()` **入口清 `_interrupt`** —— 不是 SPEAKING 入口。
  用户在 THINKING 期间（例如 `look` 正跑着）喊的那一声，要活到 SPEAKING 才生效。
- `_on_enter_speaking()`：TTS 循环每写一块 PCM 前查 `_interrupt`，置位就 break
  （PyAudio 缓冲只有 `frames_per_buffer=480` = 16kHz 下 **30ms**，残留可忽略），
  然后**响一声提示音**并 `transition(LISTENING)`
- `_on_enter_idle()`：优先级改为 **暂停中的音乐 > 待播的新歌**
- `stop_music` 工具 handler：**必须把暂停位也清掉**

### 9.5 一个会变成 bug 的坑

「暂停中」和「待播的新歌」是**两个不同的槽**。若 `stop_music` 只清后者，
用户说「别放了」之后这一轮一进 IDLE，音乐**会自己又响起来**。
这种 bug 在实车上极难查（用户只会觉得「我明明让它停了」）。**必须写测试钉住。**

### 9.6 关键词护栏（建议，待定）

「明说停」目前只能靠模型正确调用 `stop_music`。若 ASR 听岔、或模型偷懒没调，
音乐就会续播 —— 而用户是**明确说了**不要的。建议在 `_on_enter_thinking` 拿到 ASR
结果后加一层关键词护栏：命中「别放了 / 不听了 / 关掉音乐 / 停音乐」→ 直接清暂停位。

⚠️ 判据**只放音乐词**，不能用光秃秃的「停下」—— 那句多半是在说小车。
（本项目已有同类做法：`_ELICIT_NO` / `_cn_to_int` 都是这种「口语兜底」的代码护栏。）

### 10.2 遗留债务

都不是 bug，是「知道但没做」。按会不会咬人排序：

1. **`tools/vision.py` 的 `_classify` 按关键词匹配 `LookError` 的措辞**（T5 报告 §8 提出）。
   耦合的是**文案**不是结构 —— 将来改 `LookError` 的消息文字，映射会**静默退化**到
   兜底档，而 T5 的测试用的是自己构造的消息，**不会变红**。
   修法：给 `LookError` 加 `stage` 属性（`"snap"` / `"describe"`），映射改读属性。
   后果轻（用户听到「看这一眼没成功」而不是更贴切的一句），所以没在 T9 前动。
2. **`tools/music.py` 的 `_start()` 里 `self._stop.clear()` 是既有竞态**（T7 报告 §8.3）。
   若 `pause()` 的 join 超时（播放线程卡在 `av.open()` 网络超时 >3s），随后 `_start()`
   清掉 `_stop`，那个还卡着的旧线程可能**复活并与新线程一起写 Speaker**。
   触发条件苛刻，且 T7 之前就存在；T7 没改（会动到 `play()` 的既有行为）。
3. **护栏与工具重复调用的措辞瑕疵**（T8 报告 §7）：用户说「别放了」时护栏先 `stop()`
   清了暂停位，模型随后若**也**调了 `stop_music`，`stop_and_describe()` 会返回
   「现在没有在放音乐。」—— 助手可能回一句「本来就没在放」。无害，听着怪。
4. **两处只有代码审查级信心、没有实测的**：
   - `container.seek` 对 **AAC/m4a** 的关键帧偏差（cookie 只拿到 320k MP3，实测落点基本重合）
   - `_record_position` 的 `frame.pts is None` 兜底分支（手上没有无时间戳的流）
