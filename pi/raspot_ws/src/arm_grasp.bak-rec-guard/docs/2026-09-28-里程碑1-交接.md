## 1. 任务是什么

最终形态：**相机看到桌上的目标 → 机械臂自己夹起来**。
L0（点画面→臂过去夹）要把"目标在画面第 (u,v) 像素"换算成"六个关节多少度"，中间靠**退化手眼标定的 5 个标量**：
`f`(焦距,px)、`t`(相机沿光轴离夹爪尖多长,cm)、`u*`,`v*`(夹爪尖落在画面哪个像素)、`roll`(图像滚转)。
标定做法：桌上放标记点 → 臂走若干姿态 → 每拍记「关节回读 + 标记点像素」→ 最小二乘解 5 个量 → **留出样本**报残差。

## 3. ★ 实测事实（别再重新发现一遍）

| 项 | 值 | 怎么来的 |
|---|---|---|
| **相机镜头离爪尖** | **12.3 cm**（沿夹爪下扎方向） | 用户用尺子量的。**模型里的 `t` 用这个，不要用设计文档里的 120** |
| **相机装法** | **光轴∥夹爪轴，刚体**，用户 2026-09-28 确认 | 但**用户手工重新装过**（挪了位置） |
| **相机倒置** | 绕**自身光轴**转 180°（很久以前就这样） | 用户确认。⇒ `roll ≈ π`，**求解初值要给 π 不要给 0**；看照片必须**转 180° 再看** |
| **底座回读可信** | `pot_raw`(物理) 与 `field`(固件) 实测只差 **0.06°** | 我核对过 |
| **α 必须够陡** | α **浅于 ≈−65° 时相机平着往前看，瓶盖根本不在画面** | 实测：α=−79° 看得见，α=−58° 只剩抽屉壁 |
| **"看得见"的经验条件** | **α ≈ 仰角(夹爪尖→瓶盖) − 18.4°** | 从一个已验证姿态上量出来的，不是模型推的 |
| **K230 板子** | IP **DHCP 会变**（这轮从 .237 变成 .216）；**从 `/tmp/k230/latest-result.json` 的 `_peer` 读** | |
| **`k230ctl snap` 是坏的** | 报"中间产物 0 字节"，但 **RTSP 流本身是好的** | 用 `gst-launch` 直接抓（`collect.capture_frame` 已封装） |
| **标记点（瓶盖）** | `(17, 0, -12.3)` cm，x/y 从底座转轴量起、z 从底座安装面量起 | 用户量的；**用户挪过它，位置变了要重新量** |

## 4. 标定当前的结论（查到哪一步）

**脚本化那批 6 条**（`docs/samples-20260928-190746.json`）：

| 项 | 结果 |
|---|---|
| 留出集判据 | px_rms **5.26** px（阈值 5.0）❌ / cm_max 0.14 cm（阈值 1.5）✅ |
| 拟合集自己的残差 | **17.6 px**，且**随姿态序号单调变化**（26→25→13→7→…→5）= **系统性** |
| 解出的参数 | `f=8,849,631`、`t=234,762` —— **荒唐的退化解**，等价于模型想退化成正交投影 |

**逐个排查过（工具在 `tools/`）**：

| 假设 | 实验 | 结论 |
|---|---|---|
| 标记点坐标量错 | `whats_missing.py`：z 偏 −1/−2/−3/−6cm | 地板只从 16 降到 10 px → **不是它** |
| 光轴相对夹爪轴倾斜 | `verify_tilt.py` | 两种写法**不一致**（3.39 vs 20.5 px）→ **不是简单倾斜** |
| 关节零位偏置 | `offset_test.py` | 能压到 2.8px，但偏置是"肩+48.6°/底座−19.2°"这种荒唐值，换组(f,t)全变 → **不唯一，不可信** |
| 焦距/像距本身 | `pin_t.py`：把实测 t=12.3 钉死 | 残差 **22.6px，比全自由还差** → **不是 f、t 的问题** |
| 主点不在画面中心 | `whats_missing.py`：放开 u0,v0 | **22.6 → 3.39 px**，主点解出 `(659.5, 4.6)`（v0 离中心 355px！） |

**关键判断**：3.39px 那组**很可能是过拟合**——6 个样本配 6 个自由参数（12 个方程），几乎没冗余。**样本不够，分不出"主点真的偏了"还是"模型缺了别的自由度"。**

**另一个已知缺信息的地方**：这 6 个姿态的几何变化**太窄**（为了瓶盖留在画面里，夹爪尖离瓶盖只有 6.4~12.2cm、α 只在 −75°~−88°）。透视信息来自"相机到目标距离的变化"，这里只有约 15% → **f 和 t 因此不可分辨**。计划原本写的是 10~12 个姿态。

## 5. 已修的坑（**别再踩**，都是会静默污染数据的）

1. **驱动和摇杆装在同一个 service 里**。程序控臂前要 `sudo systemctl stop ps2-teleop.service`，但**停了之后必须单独起 `l150pro_driver_node`**（否则收不到 `/arm/feedback`）。
2. **`ros2 run` 会留孤儿进程**：`Popen.terminate()` 只杀启动器，真节点被 init 收养（实测 PPID=1）继续占着 `/dev/l150pro` → 和服务的驱动**抢串口** → 固件反复走 `INIT_HOME` → **INIT_HOME 期间 `/arm/feedback` 是固件总线调试计数器、不是关节角** → 回读被污染成假值。
   修法：`start_new_session=True` + `killpg`，且**起驱动前断言串口独占**、启停都清残留。
3. **颜色检测器会假阳性**：旧判据（只看 B 比 R/G 大）把**蓝白色床单**当瓶盖（26904px！）。实测瓶盖 `R37 G133 B255` vs 床单 `R169 G224 B252` → 改用**饱和度** `B>R+60 & B>G+60 & B>110` + 面积下限 500。**已加正/负样本测试。**
4. **到位判据比物理噪声还严**：原要求 6 个字段**逐位相同**持续 0.7s，而电位器底噪 ±1 count → 计时器每帧被重置 → **必然超时**。改成"抖动在 ±4 count 内稳住 0.8s"。
5. **`pgrep -f <串>` 会匹配到自己的 shell**（那条 shell 的命令行里含这个串）→ 我**杀过自己两次**。改用节点可执行文件路径做判据 + 排除自身进程链。
6. **`DOCS_DIR` 用 `__file__` 推**：`ros2 run` 跑的是 install 树 → 样本写错地方。改成**优先源码树**。
7. **`multifilesink` 没有 `num-buffers` 属性**：我第一版写错、还把 gst 报错吞了 → **静默返回 False**。改用 `timeout -s INT` + `-e`，失败要打报错。
8. **不要按"上一个读到的姿态"发绝对关节值**：用户会手动挪臂（装相机时），我因此发出过一次没打算的大动作。**一律现读→算增量→打印→再发**。

## 7. ★ 下一步：手动采集（**用户摆姿态，我们只记录**）

**为什么换成这个**：脚本走姿态时"瓶盖必须留在画面里"把姿态箱卡死了 → 几何变化不够 → f/t 不可分辨。**用户能看到画面**，让他摆姿态能同时解决"瓶盖一定在画面里""姿态可以更散""不会撞"。

**流程**：
1. 用户用手柄（`ps2-teleop.service` **不用停**）把臂摆到能看见瓶盖的姿态；
2. 摆好后叫一声；
3. 我们跑：
   ```bash
   source /opt/ros/jazzy/setup.bash && source ~/raspot_ws/install/setup.bash
   /usr/bin/python3 ~/raspot_ws/src/arm_grasp/tools/rec_sample.py \
       /tmp/k230/manual_samples.json --point 17,0,-12.3 --note "高一点"
   ```
   它会：拍照 → **用颜色独立确认瓶盖在画面里**（没有就报"这一拍不算"，不记）→ 检查跟踪器有没有漂（漂了**按颜色自动重锁**）→ 读回读（要连续两条一致才算稳）→ 存一条。
4. **要散的姿态**：高/低（夹爪尖离瓶盖 6~20cm）、近/远、底座正前/偏左 20°/偏右 20°、α 深/浅。
   ⚠️ **夹爪尖别贴到瓶盖上**（保持 3cm 以上），每条会报距离。
5. **凑到 12 条左右**，然后：
   ```bash
   ros2 run arm_grasp calib_report --samples <json> --holdout 3 --fit-principal
   ```
   （`--fit-principal` 需要 ≥7 条样本；`solve()` 里会检查）

**判据（事先约定，别改）**：`px_rms(留出) < 5 px` 且 `cm_max(留出) < 1.5 cm`。

**如果还是不通过**，按这个顺序查（design §9 / 计划 Task 6 Step 5）：
1. 标记点坐标量错？ —— **注意：实测这条的灵敏度很低**，z 偏 3cm 时残差照样"通过"，但 f 已经偏 12%（"自洽但错"）
2. 采集时跟踪器漂了？ —— 看 meta 里的 `track_vs_color_px`，>60px 的剔掉
3. `from_fields` 的 **p3/p4/p5 顺序**错了？（全项目唯一没独立验证的假设）判据：**换个姿态残差系统性变大**，而不是随机散布
4. 平行假设真的成立吗？ —— 1~3 都排除后，回头找用户
