# l150pro_driver

WHEELTEC L150Pro（C30D 2.0 主控板）**四驱差速**底盘的 ROS 2 驱动。

下位机固件是 `雷达定位版` 改造成的 ROS 执行器固件；本包是它的上位机对端。

---

## 架构分工（先看这个，别越界）

```
┌──────────────────────┐        串口1 @115200        ┌─────────────────────┐
│  STM32 (C30D 2.0)    │ ◄──── 12B 运动帧 @20Hz ──── │  树莓派 / ROS 2     │
│                      │ ◄──── 17B 舵机帧 @按需 ──── │                     │
│  · 电机闭环 PI       │                             │  · 本驱动节点       │
│  · 轮速测量          │ ──── 28B 状态帧 @50Hz ────► │  · 里程计积分       │
│  · IMU 原始量        │                             │  · EKF 融合         │
│  · 丢帧看门狗 200ms  │                             │  · TF               │
│  · 舵机 PWM          │                             │                     │
└──────────────────────┘                             └─────────────────────┘
```

**位姿解算和传感器融合在树莓派上做，不在 STM32 上。** STM32 只负责实时性要求高的
电机闭环和原始量采集。

## 安装

```bash
# 依赖
sudo apt install ros-$ROS_DISTRO-robot-localization python3-pyserial

# 串口权限（加完要重新登录才生效）
sudo usermod -aG dialout $USER

# 编译
cd ros2_ws
colcon build --packages-select l150pro_driver
source install/setup.bash
```

## 接线

| | |
|---|---|
| 串口 | 板上的 **Type-C 串口口**（对应 `USART1`，PA9/PA10） |
| 设备名 | 通常是 `/dev/ttyUSB0`，用 `ls /dev/ttyUSB*` 确认 |
| 波特率 | 115200 |
| 转换器 | **板载 CH9102F，不需要外接 USB-TTL**，一根 USB-C 数据线即可 |
| 烧录 | 走 SWD/J-Link，**和串口完全独立**，所以 Pi 可以长期插着 |

> 板上标注为"串口3 ROS 主机口"的是 `USART3`（PD8/PD9）。本固件把 ROS 协议实现在了
> **串口1**，接的时候别插错。这是既定选择，协议不受影响。

## 运行

```bash
# 驱动 + EKF
ros2 launch l150pro_driver l150pro.launch.py

# 只跑驱动，不跑 EKF
ros2 launch l150pro_driver l150pro.launch.py use_ekf:=false

# 指定串口
ros2 launch l150pro_driver l150pro.launch.py port:=/dev/ttyUSB1
```

单独调试（不启 ROS）：

```bash
python3 -m l150pro_driver.monitor --port /dev/ttyUSB0
```

监视器按 `d` 可测 **yaw 漂移率（度/分钟）** —— 这个数字决定 EKF 协方差怎么设。

## 话题

### 发布

| 话题 | 类型 | 说明 |
|---|---|---|
| `wheel_odom` | `nav_msgs/Odometry` | 轮式里程计（本节点由轮速积分得到） |
| `imu/data_raw` | `sensor_msgs/Imu` | **只有角速度可用**，见下方 yaw 说明 |
| `driver_fault` | `Int16MultiArray` | `[fault位, crc_err, head_err, dropped]` |
| `battery_voltage` | `std_msgs/Float32` | 电池电压 (V)，每个状态帧发一次 |
| `odom` | `nav_msgs/Odometry` | EKF 融合输出（由 `ekf_node` 发布） |
| `tf` | | `odom -> base_footprint` |

### 订阅

| 话题 | 类型 | 说明 |
|---|---|---|
| `cmd_vel` | `geometry_msgs/Twist` | 只取 `linear.x` 和 `angular.z`（差速车无横移，`linear.y` 被忽略） |
| `cmd_vel_stamped` | `geometry_msgs/TwistStamped` | 同上，带时间戳版本 |
| `servo_cmd` | `sensor_msgs/JointState` | `position[0..5]` → 舵机 ch1..ch6，单位**微秒**。ch5/ch6 是车体坐标，约定见下 |

---

### 云台通道的坐标约定（ch5 / ch6）

`servo_cmd` 里的值是**车体坐标系**的，不是原始脉宽 —— 客户端不需要知道舵机是怎么装的：

| 通道 | 值增大表示 | 中位 |
|---|---|---|
| ch5（水平） | 云台往**右** | 1500 |
| ch6（俯仰） | 云台往**上** | 1500 |

`0`（或 `<500`）表示**该路保持不动**，不是"转到最小"。

**为什么 ch5 要翻一次**：这颗舵机是反装的 —— 物理上脉宽变大是往**左**。驱动在出线
前翻了一次（`protocol.servo_command_to_pulse()`），所以客户端各自都不必再实现一遍
方向。历史教训：正因为以前没有这一层，语音助手和云端上位机**各自写了一遍约定，
结果两边都写反了**。

哪天把舵机装正（或换一颗不反装的），把参数 `pan_invert` 置 `false` 即可，不用改代码。

## ⚠️ IMU 的 yaw 会漂，别当绝对航向用

下位机姿态是「陀螺仪 + 加速度计」互补滤波，**磁力计从未参与**。后果：

| 角 | 参考源 | 性质 |
|---|---|---|
| roll | 重力（加速度计） | ✅ 绝对，不漂 |
| pitch | 重力（加速度计） | ✅ 绝对，不漂 |
| **yaw** | **无，纯陀螺仪积分** | ❌ **持续漂移，无绝对参考** |

加速度计在绕垂直轴旋转时提供不了任何信息，所以互补滤波对 yaw 的修正恒为零。

**因此本节点默认不发布 IMU 的 orientation**（`orientation_covariance[0] = -1`），
只发角速度和线加速度，航向由 `ekf_node` 从轮式里程计观测。

`gz`（角速度）**本身是可信的** —— 陀螺仪测量没问题，坏的只是"积分"。

### 实测漂移

| 条件 | yaw 漂移 |
|---|---|
| 冷机、静止、电机不转 | **0.17 度/分钟** |

同时实测链路质量：**50.0 Hz、CRC 错误 0、丢帧 0、故障位 0x00**。

0.17 度/分钟比消费级 MEMS 的典型值好一个数量级——下位机开机前 500 个采样的零偏标定确实有效。

**但这不能当定值用**：电机振动会让陀螺产生整流误差，热机后温漂也会改变零偏。
所以 `yaw_variance` 默认设为 `1e-2`（约 5.7° 标准差，明显悲观），而不是贴着实测值设。

### 航向来源：**只用陀螺仪，不用轮速**

本车是**滑移转向（skid-steer）**，转弯时四个轮子必须**横向擦地滑移**。所以编码器
算出来的 yaw 有**系统性误差**——每次转弯都错，而且会累积。

陀螺仪测的是车体真实角速度，**和打滑完全无关**，所以 0.17 度/分钟虽然慢但在漂，
却比"一转弯就错"的轮速 yaw 可靠得多。

`config/ekf.yaml` 里已经这么配了：

```yaml
odom0_config: [ ..., vyaw = false ]   # 不用轮速算 yaw
imu0_config:  [ ..., vyaw = true  ]   # 用陀螺仪角速度
```

**光改这一处就解决了打滑带来的航向问题**，不需要额外传感器。

> 关于磁力计：**试过了，不work，已完整撤回。** 这台车 IMU 处的静磁场约 **640 µT**，
> 而地磁只有 25~65 µT，**信噪比 <10%**，而且干扰随电池/物体位置变化（电池挪近变
> 2000 µT）。硬铁标定救不了。**yaw 就是纯陀螺仪，基线 0.17 度/分钟。不要再往这个
> 方向试了。**

## ⚠️ 标定：装车实测前，里程计数值不可信

固件里的物理尺寸已于 2026-09 换车后按实测更新（轮径 125mm、MG540 霍尔
13 线、30 减速比）：

| 参数 | 固件当前值 | 本节点对应常量 |
|---|---|---|
| 轮径 | 0.125 m | 无（固件侧换算，节点用 `wheel_scale` 吸收残余） |
| 轮距 | 0.460 m | `WHEEL_SPACING` |
| 轴距 | 0.540 m | `AXLE_SPACING` |
| 有效全轮距 W+A | **1.000 m** | `TRACK_EFF` |

**但 `track_eff` 仍是外推值，标定完成前：**

- ⚠️ 1.000 是沿用原厂"轮距 + 轴距"模型外推的。四驱滑移转向的等效轮距含
  **侧滑修正**，真值必须靠原地转标定
- ⚠️ 标定前 odom 的**航向（yaw）不要信**；距离方向对，量级应已接近真值
- ❌ **不要调 EKF 协方差** —— 会照着未标定的数据调
- ✅ 但"能不能连、能不能动、方向对不对、看门狗灵不灵、舵机动不动"**都和标定无关**，现在就能验

### 两个标定参数（都是 ROS 参数，改完不用重新部署）

**`track_eff`** —— 有效全轮距，用于从左右轮速反解角速度。

```bash
ros2 launch l150pro_driver l150pro.launch.py track_eff:=0.XXX
```

- 默认 `1.000`（= 固件里的 `W+A` = `0.460+0.540`）
- ⚠️ 是**全**轮距不是半轮距。用半轮距会让角速度**大一倍**
- ⚠️ 1.000 是**外推初值不是标定值**，标定前 yaw 不可信
- 标定：让车原地转已知角度，量实际转了多少，按比例修正
- 迭代试值用 `l150pro_monitor --track-eff 0.95`，**不用改常量重新编译**；
  量准了再把 `protocol.py` 的 `TRACK_EFF` 固化成最终值，build 一次收尾

#### ⚠️ 原地转标定：必须落地，不能把车架起来

架起来是本能反应（怕乱撞），但**那样测出来的东西根本不是有效轮距**：

- 四轮空转、**车体根本不转** → IMU yaw 全程不动 → 拿一个 ~0 的实测角去做
  除法，得出荒谬的大值（实测过：架起来会吐出 `track_eff 新值 = 330`）。而
  现象只是"标定结果离谱"，很容易怀疑到工具头上而不是流程上。
  `report_cal` 现在遇到 IMU 转角 < 0.5 rad 会**直接告警、不出数**
- 更本质的：**等效轮距这个量的物理定义就是轮胎侧滑修正**。必须在有侧滑的
  条件下才测得出来，轮子离地就没有侧滑可言——架起来测到的只是几何轮距

配套：

- **就在平时跑的那块地上标**。地毯和瓷砖的侧滑差别不小，**换场地要重标**
- 在实地上转意味着可能撞东西：转速压到 `0.3~0.5 rad/s`，清空场地再做
- 按 `c` 时车必须是**静止**的（`YawUnwrapper` 的第一帧只作基准不累加）

**`wheel_scale`** —— 轮速比例修正，补偿固件里轮径配置与实际不符。

```bash
ros2 launch l150pro_driver l150pro.launch.py wheel_scale:=X.XX
```

- 默认 `1.0`
- 标定：指令车走已知距离 `D_指令`，量实际距离 `D_实际`，则 `wheel_scale = D_实际 / D_指令`
- ⚠️ 这只修正**上报值**，不改变车的实际速度——要改实际速度得在固件里改轮径

### 测运动时指令速度仍要压低

```
实际车速 = 指令车速 × (实际轮径 / 固件配置轮径)
```

2026-09 换车后固件轮径已改对（0.125），**指令速度与实车速度现在是 1:1**：
此前固件轮径写小，实车约是指令的 **1.92 倍**。所以同样的数值会比换车前
"体感慢"，**那是修正对了，不是回归**。仍然：

- 本节点 `max_vx` 默认是保守的 **0.5 m/s**（不是常见的 1.2），标定后再调大
- 固件侧硬限幅是 **3.5 m/s**，**别靠近**
- 第一次测建议用 `0.1~0.2 m/s`

> 速度环 PI **不需要重调** —— 它闭环在"上报值"上，是自洽的，只是绝对速度不对。

## 安全约定

| 机制 | 行为 |
|---|---|
| 上电默认不动 | 固件必须收到带 `flags bit0` 的帧才动。本节点启动时会先发 10 帧零速使能帧 |
| 丢帧看门狗 | **200ms** 收不到有效下行帧，固件自动停车 |
| 退出停车 | 节点退出前会发一帧零速 |
| cmd_vel 限幅 | 本节点限 ±1.2 m/s；固件侧还有 ±3.5 m/s 硬限幅 |
| 舵机无看门狗 | **故意如此**：主机停止发送时舵机保持最后位置（云台不该乱甩） |
| 舵机中位 | 上电 6 路均为 1500us，不会突然乱动 |

## 排错

| 现象 | 检查 |
|---|---|
| 完全没数据 | ① 串口对不对 ② 波特率 115200 ③ **共地** ④ 板子有没有上电 |
| 收到乱码 | 用串口助手时**没开十六进制模式**——二进制帧在文本模式下就是乱码 |
| 帧全被 CRC 拒绝 | 检查是否接的是串口1（不是串口3） |
| 车不动 | ① 看 `driver_fault` 的 fault 位 ② 电压是否 <10V（固件会拒绝运动）③ 有没有在发 `cmd_vel`（看门狗 200ms 就停） |
| 原地打转 / 转向异常 | 检查底盘型式是否真是四驱差速；`Car_Mode` 在固件里硬编码为 `FourWheel_Car` |
| odom 角度大一倍 | 检查轮距——必须用**全**轮距 1.000 m（`0.460+0.540`），不是半轮距 0.500 |

## 给后来改代码的人

`protocol.py` 里有三处**看起来可以简化、但改了会导致与固件不一致**的地方，
都在文件头注释里说明了：

1. C 的 `(short)float` 是**向零截断**，用 `int()` 不用 `round()`
2. 用 `f32()` 模拟 float32 是为了**严格相等比对**，不是为了好看
3. wrap **必须在弧度域做**，与固件同序

另外 `MotionRxParser` / `ServoRxParser` 是固件接收侧的**逐字镜像**，
连"舵机解码器没有 head_err 计数"这种不对称都照实复刻了 —— 不要"顺手优化"，
否则对拍会产生假告警。

**协议是双方冻结的。改任何字段之前，先和固件侧确认。**
