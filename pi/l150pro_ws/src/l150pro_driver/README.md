# l150pro_driver

WHEELTEC L150Pro（C30D 2.0 主控板）**四驱差速**底盘的 ROS 2 驱动。

下位机固件是 `雷达定位版` 改造成的 ROS 执行器固件；本包是它的上位机对端。

---

## 架构分工（先看这个，别越界）

```
┌──────────────────────┐        串口1 @115200        ┌─────────────────────┐
│  STM32 (C30D 2.0)    │ ◄──── 12B 运动帧 @20Hz ──── │  树莓派 / ROS 2     │
│                      │ ◄──── 17B 舵机帧 @按需 ──── │                     │
│  · 电机闭环 PI       │                             │  · 本驱动节点       │
│  · 轮速测量          │ ──── 28B 状态帧 @50Hz ────► │  · 里程计积分       │
│  · IMU 原始量        │                             │  · EKF 融合         │
│  · 丢帧看门狗 200ms  │                             │  · TF               │
│  · 舵机 PWM          │                             │                     │
└──────────────────────┘                             └─────────────────────┘
```

**位姿解算和传感器融合在树莓派上做，不在 STM32 上。** STM32 只负责实时性要求高的
电机闭环和原始量采集。

## 接线

| | |
|---|---|
| 串口 | 板上的 **Type-C 串口口**（对应 `USART1`，PA9/PA10） |
| 设备名 | 通常是 `/dev/ttyUSB0`，用 `ls /dev/ttyUSB*` 确认 |
| 波特率 | 115200 |
| 转换器 | **板载 CH9102F，不需要外接 USB-TTL**，一根 USB-C 数据线即可 |
| 烧录 | 走 SWD/J-Link，**和串口完全独立**，所以 Pi 可以长期插着 |

> **串口1**，接的时候别插错。这是既定选择，协议不受影响。

## 运行

```bash
# 驱动 + EKF
ros2 launch l150pro_driver l150pro.launch.py

# 只跑驱动，不跑 EKF
ros2 launch l150pro_driver l150pro.launch.py use_ekf:=false

# 指定串口
ros2 launch l150pro_driver l150pro.launch.py port:=/dev/ttyUSB1
```

```bash
python3 -m l150pro_driver.monitor --port /dev/ttyUSB0
```

### 云台通道的坐标约定（ch5 / ch6）

`servo_cmd` 里的值是**车体坐标系**的，不是原始脉宽 —— 客户端不需要知道舵机是怎么装的：

| 通道 | 值增大表示 | 中位 |
|---|---|---|
| ch5（水平） | 云台往**右** | 1500 |
| ch6（俯仰） | 云台往**上** | 1500 |

`0`（或 `<500`）表示**该路保持不动**，不是"转到最小"。

**为什么 ch5 要翻一次**：这颗舵机是反装的 —— 物理上脉宽变大是往**左**。驱动在出线
前翻了一次（`protocol.servo_command_to_pulse()`），所以客户端各自都不必再实现一遍
方向。历史教训：正因为以前没有这一层，语音助手和云端上位机**各自写了一遍约定，
结果两边都写反了**。

哪天把舵机装正（或换一颗不反装的），把参数 `pan_invert` 置 `false` 即可，不用改代码。

## ⚠️ IMU 的 yaw 会漂，别当绝对航向用

下位机姿态是「陀螺仪 + 加速度计」互补滤波，**磁力计从未参与**。后果：

| 角 | 参考源 | 性质 |
|---|---|---|
| roll | 重力（加速度计） | ✅ 绝对，不漂 |
| pitch | 重力（加速度计） | ✅ 绝对，不漂 |
| **yaw** | **无，纯陀螺仪积分** | ❌ **持续漂移，无绝对参考** |

加速度计在绕垂直轴旋转时提供不了任何信息，所以互补滤波对 yaw 的修正恒为零。

**因此本节点默认不发布 IMU 的 orientation**（`orientation_covariance[0] = -1`），
只发角速度和线加速度，航向由 `ekf_node` 从轮式里程计观测。

`gz`（角速度）**本身是可信的** —— 陀螺仪测量没问题，坏的只是"积分"。

### 实测漂移

| 条件 | yaw 漂移 |
|---|---|
| 冷机、静止、电机不转 | **0.17 度/分钟** |

同时实测链路质量：**50.0 Hz、CRC 错误 0、丢帧 0、故障位 0x00**。

0.17 度/分钟比消费级 MEMS 的典型值好一个数量级——下位机开机前 500 个采样的零偏标定确实有效。

**但这不能当定值用**：电机振动会让陀螺产生整流误差，热机后温漂也会改变零偏。
所以 `yaw_variance` 默认设为 `1e-2`（约 5.7° 标准差，明显悲观），而不是贴着实测值设。

### 航向来源：**只用陀螺仪，不用轮速**

本车是**滑移转向（skid-steer）**，转弯时四个轮子必须**横向擦地滑移**。所以编码器
算出来的 yaw 有**系统性误差**——每次转弯都错，而且会累积。

陀螺仪测的是车体真实角速度，**和打滑完全无关**，所以 0.17 度/分钟虽然慢但在漂，
却比"一转弯就错"的轮速 yaw 可靠得多。

`config/ekf.yaml` 里已经这么配了：

```yaml
odom0_config: [ ..., vyaw = false ]   # 不用轮速算 yaw
imu0_config:  [ ..., vyaw = true  ]   # 用陀螺仪角速度
```

**光改这一处就解决了打滑带来的航向问题**，不需要额外传感器。

> 关于磁力计：**试过了，不work，已完整撤回。** 这台车 IMU 处的静磁场约 **640 µT**，
> 而地磁只有 25~65 µT，**信噪比 <10%**，而且干扰随电池/物体位置变化（电池挪近变
> 2000 µT）。硬铁标定救不了。**yaw 就是纯陀螺仪，基线 0.17 度/分钟。不要再往这个
> 方向试了。**

## 陀螺偏航速率闭环（`yaw_loop.py`）

### 解决什么问题

固件轮径 bug 修好、链路干净之后**落地实跑**得到：

| 指令 (vx, wz) | vx 达成 | 陀螺实测 wz / 指令 wz | 反推"有效轮距" |
|---|---|---|---|
| (0.2, −0.3) | 82% | **56%** | 1.348 m |
| (0.3, −0.45) | 78% | **48%** | 1.521 m |

两点**指令半径相同**（0.667 m），只变速度 —— 所以这 13% 的差是速度引起的。

车**系统性地只转到指令的 48~56%，而且越快越不够**。把它折算成"有效轮距"得到
两个不同的值，**它不是常数** —— 四驱滑移转向的等效轮距，物理本质就是轮胎侧滑
修正，随速度/载重/地面变。

**所以开环写死任何一个 `b` 都不可能准，调参是条死路。**

### 做法：在有传感器的环节闭环

Pi 上有陀螺（上行帧的 `gz`，50Hz，是**原始测量、可信**）。拿它当反馈去修正
发给固件的 `wz`：

```
e      = wz_ref − wz_meas                      (wz_meas 来自陀螺)
I     += Ki·e·dt          钳到 |I| <= i_clamp_frac·|wz_ref|
wz_out = clamp(wz_ref + Kp·e + I, ±max_wz_out)
wz_out = 再过速率限幅（|dwz_out/dt| <= out_rate_limit）
```

稳态时积分项自动补掉未知的增益 k，使 `wz_meas → wz_ref`，**与 k 无关**。
打滑多少、地面怎么变都无所谓，**`T_eff` / `b` 直接从问题里消失**。

积分项的稳态值就是 `wz_ref·(1/k − 1)`，所以 `i_clamp_frac` 实际上是在**声明本环
至少能补偿到多小的 k**：`i_clamp_frac=1.5` 即 `k_min = 1/(1+1.5) = 0.40`。
实测最差 0.48，留了余量。**k 低于 k_min 时它故意补不满**，那是设计边界不是 bug
（补满需要无限大的积分，而积分越大、陀螺卡死时越危险）。

### ⚠️ 默认是关的 —— 必须先验符号

**`yaw_loop_enable` 默认 `false`。** 陀螺与 `cmd_vel` 的符号目前只有**间接证据**
（从上轮实测表反推的）。判反了就是**正反馈**，车会朝反方向猛转。

代码里**刻意不提供取反参数** —— 一个配反了就是跑飞，比没有闭环危险得多。符号
只能靠现场验证，不能靠配置兜底。

#### 上机流程

```bash
# 终端 A：起驱动（闭环关着，这是默认值）
ros2 launch l150pro_driver l150pro.launch.py port:=/dev/l150pro use_ekf:=false

# 终端 B：看闭环诊断
ros2 topic echo /yaw_loop
```

**第 0 步 —— 验符号（闭环必须关着）**

发一条**小幅度**的纯转向指令：

```bash
# 终端 C
ros2 topic pub -r 20 /cmd_vel geometry_msgs/msg/Twist \
    "{linear: {x: 0.0}, angular: {z: 0.2}}"
```

看终端 B 的 `wz_meas`（第二个数）：**必须与命令同号（正）**。

- ✅ 同号 → 符号正确，继续
- ❌ **异号 → 立刻 Ctrl-C 停车，符号判反了**，说明本文档和代码的假设错了，
  需要改 `yaw_loop.py` 里的符号约定后再重来。**不要开闭环。**

**第 1 步 —— 开闭环，对比**

```bash
ros2 param set /l150pro_driver yaw_loop_enable true
```

再发同一条指令，`wz_meas` 应当**贴住 `wz_ref`**（第一个数）。开环时它只有 ~50%。

想看得更清楚就用 `rqt_plot` 画 `/yaw_loop/data[0]`、`/yaw_loop/data[1]`、
`/yaw_loop/data[2]` 三条线。

**第 2 步 —— 调增益**

| 参数 | 默认 | 怎么调 |
|---|---|---|
| `yaw_loop_kp` | 1.5 | **先只调它**，`ki` 设 0，看阶跃响应。有超调/振铃就退一档 |
| `yaw_loop_ki` | 2.5 | 再加，直到建立时间不再改善 |

```bash
ros2 param set /l150pro_driver yaw_loop_ki 0.0     # 先关积分
ros2 param set /l150pro_driver yaw_loop_kp 1.0     # 0.5 / 1.0 / 1.5 / 2.0 逐步试
```

**参数是每条消息重读的，`param set` 立刻生效，不用重启节点。**

> **这个环是延迟受限的，不是增益受限的。** 按 k=1（侧滑最小的地面，worst case）
> 算，总相位里有一大半是纯传输延迟（上行 20ms + 下行 50ms + ZOH 25ms）。
> 所以**猛推增益的收益远小于把下行提到 50Hz**。真嫌慢就去改 `cmd_rate_hz`，
> 别去推 Ki —— 那会把 k=1 时的相位裕度吃光。

### 已知限制

- **建立时间约 1.6s（k=0.5 时）**。如果一次转弯只持续 1~2s，速率要到后半段才
  收敛，**转过的角度仍然偏少**。所以验收要看**一个动作下来总共转了多少角度**，
  不能只看稳态速率 —— 稳态收敛不代表操作员觉得"丝滑"。
- **这是速度环的外环**。前进速度那个 78~82%（见"排错"）跟本环无关，它管的是
  `vx`；本环只管 `wz`。
- **不做航向保持**。`wz_ref` 在死区内（<0.02 rad/s）时闭环完全脱开、积分清零，
  刻意不去纠直行时的缓慢偏航 —— 那是另一个功能，混进来会让"发 0 就该不动"
  这条直觉失效。

### 安全设计（每条都对应一个具体的跑飞场景）

| 风险 | 处置 |
|---|---|
| 陀螺没数据 / 过期 (>0.2s) | `allowed=False` → 直通 `wz_ref`，状态清零 |
| **陀螺卡死**（恒 0，或恒在某个非零值） | "输出动了、测量没动"的滑动窗口判据。两种卡死对称生效。触发后**退回直通并 latch**，指令持续回中位 0.5s 才解除 |
| 车被顶住 / 架在架子上 | 同上（合法的触发，退回直通同样是那里最安全的行为） |
| **符号判反**（正反馈） | 异号**且幅度大到正确符号不可能达到**（`max(1.5·\|wz_ref\|, 0.3)`）持续 0.2s → latch。只看异号不行：正常反向打杆也会短暂异号 |
| 积分饱和 / 对象冻结时顶着积分 | 积分钳位正比于指令；**任何脱开都清零** |
| 输出无限放大 | 硬钳位 `±max_wz_out` + 速率限幅 `6 rad/s²` |
| 打杆太猛 → 偏航角加速度/电流冲击 | 同上那条速率限幅 |
| **欠压**：固件 <10V 拒绝运动，车不动而 Pi 还在发指令 | `allowed` 门限 `yaw_loop_min_voltage`（默认 10.5V）+ 固件 `FAULT_UNDERVOLT` 位 |
| 固件报 IMU 故障 | `FAULT_IMU` → `allowed=False`。`FAULT_ENCODER` **不管**（本环用 gz，跟轮速无关） |
| 启动预热帧 / 急停 | `allowed=False`。**闭环在强制归零之前调**，否则预热那 10 帧会爬满积分 |
| Pi 非实时、定时器抖动 | `dt` 用 `time.monotonic()` 实测，钳到 `[0.5, 1.5]×标称` |
| 直行时把陀螺零偏/噪声积出缓慢偏航 | 死区（进 0.05 / 出 0.02，带迟滞）+ 脱开清零 |

守卫触发时会打 `ERROR` 日志。**它悄悄退回直通时，现象只是"车又转不够了"**，
不看日志想不到是守卫拦下来的。

> **残余风险（诚实记下）**：陀螺真的卡死时，从投入到判定成立约 0.8s，窗口内
> 输出最大是 **4 倍指令**（`1 + Kp + i_clamp_frac`）。关键是它**正比于指令**，
> 不是绝对值 —— 操作员松杆立刻消失。0.3 rad/s 的指令对应约 1.2 rad/s、约 55 度
> 误转。这正是 `yaw_loop_enable` 默认关、且首次必须验符号的原因。

> ⚠️ **速率限幅无论闭环开不开都在起作用**（`_slew` 在所有路径的最后）。
> 所以 `yaw_loop_enable=false` 时 `wz` 虽然原样透传，但**仍是斜坡不是阶跃** ——
> 和加这个模块之前**不完全一样**。量级很小（6 rad/s²，把 0.5 rad/s 的阶跃拉成
> 约 83ms），而且方向是好的：它压的正是偏航角加速度，也就是起步冲击电流——
> 这台车供电吃紧，那本来就是要削的东西。
> 做"开环 vs 闭环"对比时注意这一条：**稳态行为完全一致，只有暂态不同**，
> 所以对比转向精度仍然有效。

### 和轮速 PI 的关系

**不需要先调轮速 PI。** 轮速 PI 闭环在**编码器**上，而转向时编码器报的轮子转了
、车却只转了 48~56% —— **编码器正是那个在撒谎的东西**。PI 调得再紧也只是让它
更精确地去追一个错的目标；轮胎横向擦地那部分它测不到，也不可能补。

偏航环闭环在陀螺上，陀螺在这些环节的**外面**，所以轮速 PI 的**增益**误差会被
偏航环的积分自动吸收 —— 这正是本环存在的意义。唯一真实的耦合是**动态特性**：
轮速 PI 若很迟钝或振荡，被控对象的时间常数会变大、陀螺上会多出振荡。测试覆盖了
`tau=0.3s`（比预估的 0.1s 慢三倍），收敛没问题，只是慢一点。

**若以后调了轮速 PI，回来重跑一遍阶跃测试即可**（两分钟），不用重调偏航环增益。

- ✅ 但"能不能连、能不能动、方向对不对、看门狗灵不灵、舵机动不动"**都和标定无关**，现在就能验

> **2026-09-20 补：`track_eff` 对转向已经不重要了。**
> 加了陀螺偏航闭环之后，转弯用的 `wz` 是陀螺反馈修正出来的，跟 `track_eff`
> 没关系了。而且 `ekf.yaml` 里本来就是 `odom0 vyaw = false`（不用轮速算 yaw），
> 所以 `track_eff` 现在唯一的去处是 `wheel_odom.angular.z` 这个**没人消费**的
> 字段。**不必再为"原地转标定"专门跑一趟**——它标出来的值也不可信（实测
> 1.35 和 1.52 两个值，因为它本来就不是常数）。真要标就当练手。

### 两个标定参数（都是 ROS 参数，改完不用重新部署）

**`track_eff`** —— 有效全轮距，用于从左右轮速反解角速度。

```bash
ros2 launch l150pro_driver l150pro.launch.py track_eff:=0.XXX
```

- 默认 `1.000`（= 固件里的 `W+A` = `0.460+0.540`）
- ⚠️ 是**全**轮距不是半轮距。用半轮距会让角速度**大一倍**
- ⚠️ 1.000 是**外推初值不是标定值**，标定前 yaw 不可信
- 标定：让车原地转已知角度，量实际转了多少，按比例修正
- 迭代试值用 `l150pro_monitor --track-eff 0.95`，**不用改常量重新编译**；
  量准了再把 `protocol.py` 的 `TRACK_EFF` 固化成最终值，build 一次收尾

#### ⚠️ 原地转标定：必须落地，不能把车架起来

架起来是本能反应（怕乱撞），但**那样测出来的东西根本不是有效轮距**：

- 四轮空转、**车体根本不转** → IMU yaw 全程不动 → 拿一个 ~0 的实测角去做
  除法，得出荒谬的大值（实测过：架起来会吐出 `track_eff 新值 = 330`）。而
  现象只是"标定结果离谱"，很容易怀疑到工具头上而不是流程上。
  `report_cal` 现在遇到 IMU 转角 < 0.5 rad 会**直接告警、不出数**
- 更本质的：**等效轮距这个量的物理定义就是轮胎侧滑修正**。必须在有侧滑的
  条件下才测得出来，轮子离地就没有侧滑可言——架起来测到的只是几何轮距

配套：

- **就在平时跑的那块地上标**。地毯和瓷砖的侧滑差别不小，**换场地要重标**
- 在实地上转意味着可能撞东西：转速压到 `0.3~0.5 rad/s`，清空场地再做
- 按 `c` 时车必须是**静止**的（`YawUnwrapper` 的第一帧只作基准不累加）

**`wheel_scale`** —— 轮速比例修正，补偿固件里轮径配置与实际不符。

```bash
ros2 launch l150pro_driver l150pro.launch.py wheel_scale:=X.XX
```

- 默认 `1.0`
- 标定：指令车走已知距离 `D_指令`，量实际距离 `D_实际`，则 `wheel_scale = D_实际 / D_指令`
- ⚠️ 这只修正**上报值**，不改变车的实际速度——要改实际速度得在固件里改轮径

### 测运动时指令速度仍要压低

```
实际车速 = 指令车速 × (实际轮径 / 固件配置轮径)
```

2026-09 换车后固件轮径已改对（0.125），**指令速度与实车速度现在是 1:1**：
此前固件轮径写小，实车约是指令的 **1.92 倍**。所以同样的数值会比换车前
"体感慢"，**那是修正对了，不是回归**。仍然：

- 本节点 `max_vx` 默认是保守的 **0.5 m/s**（不是常见的 1.2），标定后再调大
- 固件侧硬限幅是 **3.5 m/s**，**别靠近**
- 第一次测建议用 `0.1~0.2 m/s`

> 速度环 PI **不需要重调** —— 它闭环在"上报值"上，是自洽的，只是绝对速度不对。

## 安全约定

| 机制 | 行为 |
|---|---|
| 上电默认不动 | 固件必须收到带 `flags bit0` 的帧才动。本节点启动时会先发 10 帧零速使能帧 |
| 丢帧看门狗 | **200ms** 收不到有效下行帧，固件自动停车 |
| 退出停车 | 节点退出前会发一帧零速 |
| cmd_vel 限幅 | 本节点限 `max_vx`/`max_wz`（默认 0.5 m/s / 1.5 rad/s）；固件侧还有 ±3.5 m/s 硬限幅 |
| 舵机无看门狗 | **故意如此**：主机停止发送时舵机保持最后位置（云台不该乱甩） |
| 舵机中位 | 上电 6 路均为 1500us，不会突然乱动 |
| 偏航闭环 | 默认**关**。启用后另有 6 道守卫，见"陀螺偏航速率闭环"一节 |

> ⚠️ **`_cmd_estop` 目前是死代码** —— 它在 `__init__` 里初始化为 `False`，
> 在 `_tx_timer` 里被读取，但**全代码没有任何地方把它置 `True`**。
> 也就是说 `FLAG_ESTOP` 这条路从来没执行过。别把它当既有的急停能力用。
> （同样地，节点侧**没有 cmd_vel 超时**：发指令的进程若中途死掉，车会带着
> 最后那条指令一直走下去。这两个都是本次改动之前就存在的缺口，记在这里
> 免得当成已经有的保护。）

## 排错

| 现象 | 检查 |
|---|---|
| 完全没数据 | ① 串口对不对 ② 波特率 115200 ③ **共地** ④ 板子有没有上电 |
| 收到乱码 | 用串口助手时**没开十六进制模式**——二进制帧在文本模式下就是乱码 |
| 帧全被 CRC 拒绝 | 检查是否接的是串口1（不是串口3） |
| 车不动 | ① 看 `driver_fault` 的 fault 位 ② 电压是否 <10V（固件会拒绝运动）③ 有没有在发 `cmd_vel`（看门狗 200ms 就停） |
| 原地打转 / 转向异常 | 检查底盘型式是否真是四驱差速；`Car_Mode` 在固件里硬编码为 `FourWheel_Car` |
| odom 角度大一倍 | 检查轮距——必须用**全**轮距 1.000 m（`0.460+0.540`），不是半轮距 0.500 |
| **车只转到指令的一半** | 这是**滑移转向的固有现象**（实测 48~56%），不是故障。治本靠偏航闭环，见上 |
| **开了闭环但车还是转不够** | 看日志有没有"陀螺卡死"/"符号相反"的 ERROR（守卫退回直通了）；以及 `yaw_loop_max_wz_out` 是否 < 2×`max_wz` |
| `wz_meas` 一直是 `nan` | `/yaw_loop` 在还没收到陀螺前发 `nan`（区分"没数据"和"卡死在 0"）。一直 `nan` = 没有上行帧 |

## 给后来改代码的人

`protocol.py` 里有三处**看起来可以简化、但改了会导致与固件不一致**的地方，
都在文件头注释里说明了：

1. C 的 `(short)float` 是**向零截断**，用 `int()` 不用 `round()`
2. 用 `f32()` 模拟 float32 是为了**严格相等比对**，不是为了好看
3. wrap **必须在弧度域做**，与固件同序

另外 `MotionRxParser` / `ServoRxParser` 是固件接收侧的**逐字镜像**，
连"舵机解码器没有 head_err 计数"这种不对称都照实复刻了 —— 不要"顺手优化"，
否则对拍会产生假告警。

**协议是双方冻结的。改任何字段之前，先和固件侧确认。**
