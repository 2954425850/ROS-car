# K230 视觉链路设计（K230 ↔ Pi ↔ 云）

- 日期：2026-09-17
- 状态：设计已定稿，待出实现计划
- 涉及三台机器：K230（庐山派 `k230_canmv_lckfb`）、Pi（nepu, 192.168.1.108）、云服务器

---

## 1. 需求（只有三条，其余都是实现手段）

**R1 常态**：K230 本地跑视觉，把**结构化结果**（不是图像）传给 Pi。Pi 不关心视觉算法，只当接收方。

**R2 按需**：Pi 能打开 K230 的摄像头。两种用法：
- 拍一张照片 → 交给 `voice-chatbot` 的云端 AI 做图像分析（**AI 端接入不在本项目范围，本项目只保证照片能被取到**）
- **一直看摄像头界面**（会话式实时预览，使用频率较低，但要能随时开、用完关）

**R3 视频上云**：K230 把图像传给云服务器上的前后端。上位机可以看**原画**，也可以看**视觉处理后（原画 + 框）**的画面。
**不需要同时看两路**，可以切换。**"处理后画面" = 原画复制一份加上框**，不含掩码/分割等逐像素内容。

### ⚠️ 必须记录的"错误结论"，别重蹈

设计早期有两次被推翻的结论，原因都是**测量方法错**，不是硬件问题：

1. **"K230 WiFi 不可用"（0.04~0.16 Mbps、丢包 57%）—— 错。**
   真实原因是**在 `sta.connect()` 之后十几秒就开测，链路还没预热**（速率自适应未爬升）。
   同一条链路预热后同样的代码测出 **12.2 Mbps、零丢包**（300 倍差距）。
   **教训：测 WiFi 吞吐必须等连接稳定后再测；不要用连接刚建立时的数字下判断。**

2. **"媒体必须经过 Pi 转发"—— 错。** 这是从结论 1 推出来的。K230 有能力自己联网推流。

3. **不要用 MicroPython socket 的数字代表"K230 的网络能力"。** 原生 C 路径（RTSP/MPP）和 MicroPython 路径是两套东西。早期把两者混为一谈导致误判。

4. **跑 RTSP 例程把板子跑挂过一次**（Ctrl-C 打断推流后，MPP 资源不释放，再跑报 `MediaManager link failed(9)`，REPL 完全无响应，需断电重上电）。**这是可靠性问题，必须在设计里处理。**

## 3. 最终架构

```
┌─ K230（庐山派 · CanMV · 保留 MicroPython 跑视觉）
│   摄像头 GC2093 1080p60
│   │
│   ├─ KPU 视觉推理
│   │    └─ 结构化结果 JSON {归一化框, 类别, 置信度, 帧号/时间戳}
│   │         ├── 小 TCP → 云后端（几 KB/s）
│   │         └── 小 TCP → Pi（几 KB/s）
│   │
│   ├─ VENC chn0：720p30 H.264 @1.5~2 Mbps
│   │    └─ 裸 H.264 over TCP（非阻塞 + EAGAIN 丢帧）────────┐
│   │                                                        │
│   └─ VENC chn1：720p30 H.264                              │
│        └─ 原生 RTSP 服务端（局域网，会话式）                │
│             ├── Pi 拍一张 → 抓帧 → 断开                     │
│             └── Pi 看界面 → 持续收 → 用完断开               │
│                                                            │
├─ 云服务器（公网）  ◄───────────────────────────────────────┘
│   ├─ TCP 收裸 H.264 → ffmpeg -c copy（不转码）→ mediamtx
│   │    └── WebRTC(WHEP) / HLS → 浏览器前端（原画）
│   ├─ 结构化结果 → WebSocket → 前端 canvas 叠框
│   │    └── 「原画 / 带框」切换 = 前端一个开关，零带宽代价
│   └─ 前后端 = 已有的那套
│
└─ Pi（nepu）
    ├─ 常驻小进程：收结构化结果
    ├─ 按需：从 K230 拉 RTSP → GStreamer 解码 → v4l2loopback
    │    └── /dev/video0（真摄像头设备，任何程序可打开）
    │         └── 拍照 → 交给 voice-chatbot 的云端 AI
    └─ **不转发任何媒体** → SLAM / 路径规划 / 语音助手 零影响
```

### 各部分为什么这么切

**把协议复杂度全部赶出 K230。** K230 侧不实现 RTMP、不实现 SRT、不实现 WebRTC、不实现 RTP 打包 —— 只做一件事：把编码器吐出的 H.264 字节 `send()` 出去。所有媒体协议、封装、转 WebRTC 都在云服务器上做（ffmpeg/mediamtx + 无限算力）。**在最弱的设备上写最少的代码。**

**Pi 的 4 个核一点都不给媒体转发。** 只收几 KB/s 的结果 + 按需拉流。

**"两个都跑"用方案 A。** 只推一路**原画**，框以结构化坐标单独发，前端在 canvas 上叠加。想切换就是前端一个 checkbox，**零带宽代价**；多个客户端还能各看各的。

## 4. 接口定义

### 4.1 视频推流（K230 → 云）

| 项 | 值 |
|---|---|
| 承载 | 裸 TCP，K230 主动连云端（出站，天然穿透 NAT，不需要打洞/TURN） |
| 载荷 | H.264 Annex-B 字节流，**无任何容器/协议封装** |
| 分辨率/帧率/码率 | **720p30** @ 1.5~2 Mbps（可调）—— **25fps 硬件拿不到**，见 §7 V6 |
| K230 侧行为 | **整帧原子发送**；某帧超时/出错 → **断开重连**（本平台**无法请求 IDR**，见下）。**绝不发半帧、绝不丢单个 NAL** |

**为什么必须丢帧而不是缓冲**：MicroPython 堆只有 ~3.9 MB。网络一卡，若把帧堆进发送缓冲，板子会因内存压力崩溃。宁可掉帧，不可堆积。

**但丢的必须是「整帧」，不能是「半个帧」或「单个 NAL」** —— H.264 的 P 帧有参考链，残缺 NAL 会污染整条流直到下一个 I 帧。所以策略是：**整帧要么整帧发完、要么整帧不发**；发到一半发现 socket 堵了，就断开重连并请求 IDR，配合 GOP=25 帧（30fps 下 0.83 秒）让损伤 1 秒内自愈。

**断线期间仍必须把码流取走并丢弃（2026-09-17 实测加的，别漏）**：VENC 的输出队列只有 8 个缓冲
（`SetOutBufs(chn, 8, ...)`）。接收端消失时，**如果只是"不发了"，队列会被填满、MPP 侧没有可用输出缓冲、
管线被顶住**。所以「要么立刻发走，要么立刻丢弃」这条铁律**在断线期间同样适用**：连接断了也要
`GetStream → ReleaseStream` 把它丢掉。
实测依据：接收端消失 9 秒，板子按帧丢弃 253 帧、完整存活 45 秒不崩（Task 3）。

**接收端必须在 SPS/IDR 上同步（云端实现方的硬要求）**：重连后流是从 P 帧接上的 —— 实测重连后
**起手 14 个 NAL 全是 P 帧**，第一个 SPS 在偏移 **118816 B（≈0.46 s）** 处。P 帧没有参考帧，**不可解码**。
所以云端的收流器（以及任何消费端）**必须丢弃直到首个 SPS/IDR 再开始解码/统计**，否则前半段是花屏或直接报错。

**恢复时间上界 = GOP**：本平台 `Encoder` **没有请求 IDR 的接口**（`dir(Encoder)` 实测只有
`SetOutBufs` / `Create` / `Start` / `Stop` / `Destroy` / `GetStream` / `ReleaseStream` / `SendFrame`），
无法主动要关键帧。所以任何一次重连后的恢复时间上界就是 `gop_len=25` 帧 ≈ **0.83 s**（30fps），
再加回退重试 ≤1 s，合计 **≤1.8 s**。**这也是 GOP 必须短的原因**（见 §5 决策表）。

**实测重连频率（2026-09-17，30 分钟长稳）——云端收流器必须按此设计**：
1900 s 内发生 **~57 次真实断连**（平均每 33 s 一次），每次 **≤1.6 s 自愈**，
累计只损失 **1.8%** 的时间，**吞吐完全不受影响**（总 455,978,473 B = 平均 1.920 Mbps，
每分钟采样全部落在 1.5~2.2 Mbps）。断连成簇出现，簇外可连 200 s 不断。
→ **云端收流器必须具备「重启管道 + 丢弃到首个 SPS/IDR」的能力**，否则每次断连都会让
解码端报错或花屏。30 分钟要重启 ~57 次管道，这是硬要求不是边角情况。
（断开判据是「单帧 0.5 s 发不完」；实测与短写不区分，机制未定位，不下断言。）

> 2026-09-17 修正：本节初稿写的「EAGAIN 就丢帧」是错的，已按上述策略改正。

### 4.2 结构化结果（K230 → 云 / K230 → Pi）

```json
{
  "ts": 1789631000123,
  "frame": 84213,
  "w": 1280, "h": 720,
  "objs": [
    {"cls": "person", "score": 0.87, "box": [0.31, 0.22, 0.48, 0.91]}
  ]
}
```

- **`box` 用归一化坐标 0~1**（左,上,右,下）：这样"推理分辨率"和"推流分辨率"彻底解耦，以后改任一分辨率都不用动前端。
- 频率 ~10 Hz，量级几 KB/s（即使 MicroPython socket 也绰绰有余）。
- **帧对齐必须用 `frame`，不能用 `ts`**（见下方注意）。允许几十 ms 错位。
- **注意 `ts` 实际只有秒级精度**：2026-09-17 实测本平台 `time.time()` 返回**整数秒**（`type` 是 `int`），
  所以上面样例里 `1789631000123` 这种毫秒 epoch **拿不到**，实际发出来尾数恒为 `000`。
  - → **云端/前端请用 `frame` 做帧对齐键**；`ts` 只能当「大概是哪一秒」用。
  - → 若将来确实需要毫秒级时间，得改用 `ticks_ms` 发**相对**时间戳（从启动算起），在消费端建立基线。
  - → **另注意**：任何用 `time.time()` 做定速/计时的代码在本平台都是坏的 —— 实测一个目标 10 Hz 的
    循环跑成了 24.55 Hz（`time.time()` 差值恒为 0，节拍器退化成空操作）。**定速/计时一律用
    `ticks_ms`/`ticks_diff`。**

### 4.3 Pi 取流（K230 → Pi，局域网）

- URL：`rtsp://<k230-ip>:8554/<stream>`（原生服务端）
- 传输：**抓帧用 TCP**（稳），**看界面用 UDP**（低延迟、可容忍掉帧）
- Pi 侧管线：`rtspsrc → decodebin → v4l2sink`（喂进 v4l2loopback）
- 结果：Pi 上出现 `/dev/video0`，任何程序可当普通摄像头打开

> 实际交付的是「拉 RTSP 抓一张 JPEG」+「常驻收结构化结果」。
> **`/dev/video0`（v4l2loopback）没做** —— 需要装内核头 + 编译 DKMS 模块
> （本机 `linux-headers-6.8.0-1064-raspi` 与 `v4l2loopback` 当时都没装），
> 用户 2026-09-17 决定留到以后。
> 另外 **Pi 侧的 `decodebin` 当时根本不可用**（整个 GStreamer 没有任何 H.264 解码器），
> 实际用的是 `rtspsrc ! rtph264depay ! h264parse ! avdec_h264`。
> **「看界面」不需要 Pi 端任何代码**：任何设备直接拉 `rtsp://192.168.1.112:8554/k230` 即可。

## 5. 关键决策与理由（含被否决的方案）

| 决策 | 选择 | 理由 / 否决了什么 |
|---|---|---|
| 推流协议 | **裸 H.264 over TCP** | 否决 RTMP/SRT/RTSP push —— 那要在 K230 上实现协议（FLV 封装 / RTP 打包 / UDT），代码量和风险都远大于「把字节写进 socket」。协议复杂度放云端，ffmpeg `-c copy` 直接吃 |
| 分辨率/码率 | **720p30 @1.5~2 Mbps** | 否决跟随 1080p60（实测那条流 6.96 Mbps）—— 场景是"看画面+看框"，720p 够，换来空口和上行 5 倍余量。**2026-09-17 实测修正：原写 720p25，但 gc2093 只有 30/60/90 档、25 拿不到（§7 V6），用户决策接受 720p30** —— 带宽约束（本方案真正的目的）不受影响，实测 2.02 Mbps 仍在窗口内 |
| Pi 打开摄像头 | **RTSP 拉流**，不是 UVC | 否决 UVC：`media/uvc` 是主机侧驱动；要用 UVC Device 得自己编固件（Enable CherryUSB Device + UVC，且可能与 MicroPython 冲突）。**代价是拿已跑通的一切去换一个未验证的固件改造**。而且 UVC 只能传 MJPEG（不支持 H.264），1080p30 要 30~60 Mbps，比 H.264 高 5~10 倍 |
| `/dev/video0` | **Pi 侧 v4l2loopback** | 用一层软件换掉一次固件改造，且 Pi 上得到的是真设备，OpenCV/ROS/浏览器都能直接开 |
| Pi 的角色 | **零媒体转发** | 否决"Pi 中继" —— 那会让 ch1 空口占用从 2 Mbps 涨到 8 Mbps，并吃掉单核 10~20% |
| 原画/带框 | **方案 A：单流原画 + 归一化坐标 + 前端叠框** | 否决双流（带宽翻倍）；否决硬件 OSD 烧框（框被烧死进码流，前端无法自由渲染/切换） |
| 回滚方式 | 项目**不上 git**，靠开工快照 | 沿用本机既有习惯：`tar czf <proj>.bak-$(date +%Y%m%d-%H%M%S).tar.gz --exclude=logs --exclude=__pycache__ <proj>`；改文件前先留时间戳备份副本。**写实现计划时不要生成 git commit 步骤** |

## 7. 风险与未验证项

| # | 项 | 影响 | 备注 |
|---|---|---|---|
| V1 | **家宽上行能否稳定扛 1.5~2 Mbps** | 决定云端码率上限，是唯一的外部依赖 | **用户明确说暂缓，先不管** |
| V2 | **K230 满载余量**：推理 + 双编码 + 推流 + RTSP 同时跑的 CPU/内存 | 决定能不能真的同时做三件事 | 板子上一测就知道 |
| V3 | **MicroPython 非阻塞推流循环的稳定性** | 12.2 Mbps 测的是纯打流，真实场景要「读编码器 → 发送」 | 板子上一测就知道 |
| V4 | **MPP 资源异常中断不释放** | 线上会挂（已挂过一次） | 需看门狗 + 避免中断时打断管线。**2026-09-17 定性：TCP 层断线不触发 V4** —— 实测接收端消失 9 s，板子按帧丢弃 253 帧、完整存活。V4 的真实形态是「同一会话内无法重建管线」，见 V7 |
| V5 | **双编码通道混用**：chn0 由 MicroPython 读走、chn1 交给原生 rtspserver | 这是没试过的组合 | VENC 有 4 通道，理论可行，需验证 |
| V6 | ~~**25fps 拿不到**~~ | **已决：接受 720p30** | 2026-09-17 实测：gc2093 只有 30/60/90 档；`Sensor(fps=25)` **被静默忽略**回落 60 档，且 `src_frame_rate=25` 当除数会把码率放大到 4.2 Mbps；`dst_frame_rate` 在本 build **不丢帧**。用户当天决策：改规格为 720p30。实测 2.02 Mbps / dropped=0 / GOP 精确 25 帧 |
| V7 | **同一 MicroPython 会话内无法重建管线** | 任何「进程内重建管线」的恢复策略都不成立 | 实测：cleanup 完整（`sensor.stop`/`del link`/`encoder.Stop+Destroy`）后建第二条仍报 `MediaManager link failed(9)`。**生产 `app.py` 一进程一条管线，不受影响** |
| V8 | **装了自启之后 raw REPL 够不着** | 运维层面的恢复手段变少：`soft-reset` 与 `machine.reset()` **都需要先进 raw REPL**，因此**同时失效** | 2026-09-17 实测：板子在跑自启的 `app.py` 时 `mpremote` 报 `could not enter raw repl`，同时串口在刷 `connect to server faild!`（**板子活着**）。→ **真退路只有两条：读卡器改/删卡上 `main.py`，或把 USB 拔到另一台主机上跑 mpremote。** 另注意：**板子一上电就自动推流 ~2 Mbps，REPL 进不去，想让它在推流状态下停下来只能断电或拔卡** |

## 8. 实施顺序（分阶段，每阶段可独立验证）

**P0 — 最小闭环：K230 推流上云**
K230 出 720p30 H.264 → 裸 TCP → 云收流 → ffmpeg → mediamtx → 浏览器能看。
*验证*：浏览器里看到画面，且 K230 不崩、不堆积。

**P1 — 视觉与叠框**
K230 跑 Kmodel 推理 → 结构化结果 → 云后端 → WebSocket → 前端叠框；同时发给 Pi。
*验证*：前端能切换"原画/带框"，框与画面对齐。

**P2 — Pi 侧取流**（**2026-09-18 交付时已缩减，见下**）
K230 chn1 RTSP → Pi `rtspsrc → h264parse → avdec_h264` → 抓一张 JPEG。
*实际验证*：`k230ctl snap` 连续 10 次全部成功、cv2 可解、人工目视确认为真实画面；
`k230-resultd` 常驻收到 K230 的结果并可自愈断连。
**未做**：`v4l2loopback`/`/dev/video0`（用户决定延期）、接进 voice-chatbot（用户决定不做）。

**P3 — 可靠性**
看门狗、断线重连、丢帧策略验证、V2/V3/V5 实测、异常恢复（避免 V4）。

## 9. Pi 侧实现后的更正（2026-09-18）

实现计划：`docs/plans/2026-09-17-k230-pi-side-plan.md`
对接说明：`docs/K230-Pi端对接说明.md`；全部实测记录：`NOTES.md`

### 设计文档里被实测推翻/补上的几处

1. **§4.3 写的 `decodebin` 用不了**：Pi 上 GStreamer **一个 H.264 解码器都没有**，
   必须补装 `gstreamer1.0-plugins-bad`（`h264parse`）+ `gstreamer1.0-libav`（`avdec_h264`）。
2. **`rtph264depay` 默认吐 AVCC（长度前缀），不是 Annex-B** —— 实测文件里 `00 00 00 01` 出现 0 次。
   所以 `h264parse` 是**必需**的，不是可选。
3. **§4.3 建议「抓帧用 TCP」要打个折扣**：实测 TCP 与 UDP 都能拉通，
   但 RTSP 拉流会**偶发起手就死**（`gst_rtspsrc_loop_interleaved: Could not receive message. (Parse error)`），
   约 1/10 次。机制未定位。对策是**重试**（`snap` 已内置 3 次）。
4. **新增一条设计时不知道的强耦合：板子的推流有没有接收端，会决定 Pi 侧拿到的一切。**
   无接收端时板子主循环被失败重连拖慢：

   | | 无 8555 接收端 | 有 8555 接收端 |
   |---|---|---|
   | RTSP 帧率 | ~8.4 fps | ~30 fps |
   | 结果上报频率 | **~0.9 Hz** | **~9.5 Hz** |

   → 云端上线后 Pi 侧的体验（拍照速度、结果频率）**应当**同步变好，**但这条还没实测**。
5. **§4.2 写「频率 ~10 Hz」在有接收端时成立（实测 9.5 Hz），无接收端时不成立（0.9 Hz）。**
