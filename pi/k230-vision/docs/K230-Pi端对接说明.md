## 1. 两个能力

| 能力 | 怎么用 | 产物 |
|---|---|---|
| **拍一张照片** | `k230ctl snap` | JPEG，路径打到 stdout；稳定路径 `/tmp/k230/latest.jpg` |

> ⚠️ 产物都在 `/tmp/k230/`，而 **`/tmp` 是开机清空的**（实测 `D /tmp 1777 root root 30d`）。
> 重启后 `latest.jpg` / `latest-result.json` 会消失，分别要等下一次 `snap` / 下一条结果才回来。
> **要跨重启保留就自己加 `-o` 指到别的目录。**
| **拿视觉结果** | 常驻服务 `k230-resultd` | `/tmp/k230/latest-result.json`（最近一条） |

```bash
IMG=$(/home/cy/k230-vision/pi/k230ctl snap)     # 一行路径
/home/cy/k230-vision/pi/k230ctl result --json   # 最近一条结果
```

## 2. 照片

- **1280x720 JPEG**，质量 90，典型 40~55 KB。
- **耗时实测 2.8~7.6 s（均值 ~6.3 s）**。慢的原因是板子的 RTSP 帧率低：
  **板子没有视频接收端时只有 ~8.4 fps**，攒够一个 GOP（25 帧）就要 3.6 s。
  云端接上视频后预计回到 1~2 s 量级 —— **但这还没实测过，别当已知结论。**
- **`snap` 会自动重试 3 次**：RTSP 拉流偶发起手就死（偶发率约 1/10），
  属于快速失败，重试很划算。
- **`suspect=true` 时画面可能不可靠**（没跨过 IDR）。`--json` 会给出 `frames`。
  默认 `--min-frames 30` 已经留了余量，正常情况不该出现 `suspect`。

## 3. 结构化结果

一行一条 JSON，换行分隔，来自 K230：

```json
{"ts": 1789690497000, "frame": 2080, "w": 1280, "h": 720,
 "objs": [{"cls": "orange", "score": 0.323, "box": [0.3188, 0.5844, 0.7219, 0.9938]}]}
```

- **`box` 是归一化坐标 0~1**，`[左, 上, 右, 下]`，直接乘显示尺寸即可，**不需要任何标定**
  （已验证 AI 帧与推流帧取景完全重合）。
- `cls` 是 **COCO 80 类**名。`objs` 可能是空数组。
- `w/h` 是**推流分辨率**（1280x720），不是推理分辨率（320x320）。
- `frame` 单调递增，**做帧对齐只能用 `frame`**。
- **`ts` 只有秒级精度**（K230 的 `time.time()` 返回整数秒），尾数恒为 `000`。只能当「大概是哪一秒」。

`resultd` 会额外加两个字段：`_received_at`（Pi 收到的时刻）、`_peer`（来源地址）。

### ⚠️ 3.1 上报频率取决于板子的推流有没有接收端

| 板子的 8555 视频接收端 | 结果上报频率 |
|---|---|
| 有（云端在收） | **~9.5 Hz** ✓ 与设计一致 |
| **没有（当前状态，云端未部署）** | **~0.9 Hz** |

同一原因也会把 RTSP 帧率从 ~30 fps 压到 ~8.4 fps。
**「结果怎么半天一条」先去看板子的视频有没有人收，不是 Pi 侧的问题。**

## 4. 边界说明

- **Pi 不做任何媒体转发。** 想「看界面」不需要 Pi 参与 ——
  任何设备直接拉 `rtsp://192.168.1.112:8554/k230` 即可（VLC/mpv 都行）。
- **`/dev/video0` 未实现**（2026-09-17 用户决定延期，需要装内核头 + DKMS 模块）。
- **没接进 voice-chatbot**（同样是用户决定；本轮只保证「照片取得出来」）。
- **结果流是「最新值」语义，不是可靠传输**：只保留最近一条，不排队、不存历史。
- 排错与全部实测记录（含失败与更正）：`/home/cy/k230-vision/NOTES.md`
  和 `pi/README.md`。
