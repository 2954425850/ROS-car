## 3. 结论

### ① 两轴都没有可测的死区，小到 11µs / 1.0° 就动

pan 一路测到 **1.0°（11µs）** 都有干净的响应（内点 633）。**不存在"小指令推不动"的门槛。**

### ② 两轴的**像素灵敏度几乎一样**：约 **17 px/度**

- pan：15/1.0、17/1.5、34/2.0、52/3.0、67/4.0、104/6.0、223/12.0、426/25.0 → ≈ **16.8 px/度**
- tilt：50/3.0、111/6.0、246/12.0、462/25.0 → ≈ **17~18 px/度**

**这与 `CenterConfig` 里 `k_pan=38.0` / `k_tilt=16.0` 差 2.4 倍并不矛盾** ——
偏差归一化时 pan 除以**宽**(1280)、tilt 除以**高**(720)，所以"每归一化单位对应多少度"本来就不该相等：

| 轴 | 像素/度 | 归一化/度 | deadbeat k（度/单位） | 取一半 | `CenterConfig` |
|---|---|---|---|---|---|
| pan | 16.8 | 16.8/1280 = 0.01313 | 76.2 | 38.1 | **38.0** ✅ |
| tilt | 17.5 | 17.5/720 = 0.02431 | 41.1 | 20.6 | **16.0**（比一半更保守） |

**pan 的 38.0 几乎是"deadbeat 的一半"**，与 `t_camcalib.py` 的输出口径一致；
**tilt 的 16.0 比一半还保守**（更慢），鉴于 tilt 机械行程更小，保守方向是对的。

### ③ ⚠️ 推翻了 `t_camdeadband.py` 文件头那条前提

原文写：

> 端到端跑居中时，**tilt 连着发了 3 次 4.5°（约 50us），画面一动不动**；
> 而标定里发 10°（111us）却能测到 221 像素的位移。差别很可能是**静摩擦/舵机死区**。

**本次实测：tilt 单次 3.0°（33µs）就干净地动了 50px（内点 690）。**
13.5°（3×4.5°）不该"一动不动"。

所以那次观测**要么是配准失败报了个 0**（本文件 §1 的 +763px/内点5 就是同一类故障的现场，
`shift_between` 在内点 <8 时**直接返回 (0,0,0,0)** —— 表现得正是"一动不动"），
**要么**当时云台上还有别的发布者在写 `/servo_cmd`。**两种都没排除**，但**"存在静摩擦死区"这个解释已被实测否定。**

### ④ 对设计的影响：**不需要静摩擦累积补偿**

原计划（`2026-09-20-gimbal-track-design.md` 草案）里有一个"误差累积到超过死区才动"的机制，
它是专为对付一个**实测并不存在的死区**而设计的。**取消它**，控制律退回简单比例 + 死区。

### ⑤ `max_step_tilt = 4.5°` 偏小

25° 能转 462px，4.5° 只是零头。目标偏半屏时会被这个上限掐住，响应变慢。
**第 4 步实车调参时优先抬这个值。**

## 4. 复现方式

```bash
ssh cy@<pi>
source /opt/ros/jazzy/setup.bash
cd ~/k230-vision/pi && python3 -u t_camdeadband.py   # 大步长曲线
cd ~/k230-vision/pi && python3 -u t_pandead.py       # pan 小步长补测
```

⚠️ 两个脚本都必须**用 `systemd-run --user` 起瞬态单元**跑（或用 `setsid nohup` 脱离 SSH），
且 python 要加 **`-u`** —— 否则 stdout 块缓冲，重定向到文件时中途什么都看不到。
