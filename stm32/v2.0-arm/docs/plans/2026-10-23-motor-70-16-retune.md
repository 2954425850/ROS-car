# 再换电机（70:1 / 16 PPR）+ 速度环接回闭环

日期：2026-10-23　　范围：固件 V2.0（机械臂版）
状态：代码已改完，`BALANCE/balance.c`、`BALANCE/system.c`、`BALANCE/robot_select_init.c`、
`HARDWARE/motor_ext.c` 已用 armcc 逐文件编译通过（0 error / 0 warning）；**尚未上车实测**。

## 1. 硬件变化

| 项目 | 旧 | 新 |
|------|----|----|
| 减速比 | 30:1 | **70:1** |
| 编码器 | 13 PPR | **16 PPR** |
| 轮胎 / 底盘 / 驱动板 / 接线 | — | 不变（125 mm，外接驱动板） |

## 2. 两个必须同步改的量

**编码器折算**（`Robot_Init` → `Encoder_precision`）：

```
旧  4 × 13 × 30 = 1560  count / 轮圈
新  4 × 16 × 70 = 4480  count / 轮圈      （4 = 四倍频，EncoderMultiples）
```

`Get_Velocity_Form_Encoder()` 用 `count × 100 × 周长 / Encoder_precision` 换成 m/s，
所以这个常数同时决定**速度环的测量值、OLED 显示的实测速度、上行帧 `RosUp.vA..vD`**。
不改的话读数会快 2.87 倍，闭环会直接把车往反方向推。

**被控对象增益**：同一占空比下，轮速变成原来的 30/70 = 0.43 倍，
所以 `Velocity_KP / Velocity_KI` 按 70/30 放大：

```
Velocity_KP  2500 -> 5800
Velocity_KI   350 ->  820
```

这是**一次线性换算，不是实测值**。2026-09-20 那组参数是在旧电机上量出来的
（0.3 m/s，上升 0.42 s，稳态误差 <1%），换了电机后必须重测，见第 5 节。

## 3. 控制路径：从开环接回闭环

2026-10-16 的第一步是开环（`Target` 直接换算占空比，PI 被编译掉）。现在编码器回来了：

```
Balance_task (100Hz)
  Get_Velocity_Form_Encoder()            编码器 -> m/s
  Incremental_PI_C(MOTOR_C.Encoder, ...) 右轮
  Incremental_PI_A(MOTOR_A.Encoder, ...) 左轮   -> +-16800 count
  MotorExt_SetPwm()                      +-16800 -> +-95% 占空比
     - 保留 MOTOREXT_*_FORWARD_IS_POS 的接线方向修正
     - 保留 MOTOREXT_SLEW 斜坡（420 count/拍 = 10%/10ms）
```

`MOTOREXT_PWM_FULL_SCALE = 16800`：PI 的满量程映射到 95% 占空比，
所以闭环增益与当年板载驱动时的意义一致，`Velocity_KP/KI` 只需要按减速比缩放。

停车（失链 / 失能 / 欠压 / 急停）时除了 `MotorExt_Brake()` 还会调
`Incremental_PI_Reset()`。增量式 PI 的积分器就是输出本身，不清零的话
重新使能会从上次的占空比直接起跳。

## 4. 台架验证（**轮子离地**，顺序不能变）

1. 编译下载，上电：两个通道应是制动（INA=INB=低，占空比 0），车不动。
2. 上位机链路起来，使能，发 **0.05~0.1 m/s** 的 `vx`。
3. 看 OLED 的实测速度（`show.c` 同一行显示目标与实测）：
   - **A、C 的实测值必须与目标同号**。A=左轮，C=右轮。
   - 同号 → 负反馈成立，继续。
   - 反号 → 编码器接反，**不要**去改 `MOTOREXT_*_FORWARD_IS_POS`
     （那只会把负反馈变正反馈）。处理方式二选一：
     ①把该电机编码器的 A/B 两根线对调；②在 `Get_Velocity_Form_Encoder()`
     的 `FourWheel_Car` 分支里把该路的正负号翻过来。
   - 实测恒为 0（编码器没接上/没供电）→ **立刻停止测试**。闭环会把占空比
     顶到 95% 让车全速冲出去，这比开环危险。
4. 方向无误后，逐步加到 0.2~0.3 m/s，确认两轮同向、转向正确。

### 编码器折算的独立验证

`4 × 16 × 70` 假设新电机标称的 16 PPR 是"每转每通道脉冲数"、并且四倍频解码。
如果厂家口径不同，会整体差 2 或 4 倍，表现是**车实测速度与指令速度成比例地不一致**：

- 地面 1 m 直线，发 0.3 m/s，应约 **3.33 s** 走完；
- 若明显偏快/偏慢且比例固定，先怀疑 PPR 口径，再怀疑轮胎直径是否真是 125 mm。

### A 电机编码器损坏的处理（2026-10-23 追加）

A 电机编码器坏了，但 A、B 电机是**并联**在同一个驱动通道上的（M+ 接 M+，M- 接 M-），
两者本来就同速，所以让 B 的编码器代表整个左侧：

- `HARDWARE/encoder.h` 新增 `LEFT_ENCODER_IS_B`（默认 1）；
- `Get_Velocity_Form_Encoder()` 在算完四路速度后把 `MOTOR_B.Encoder` 抄给
  `MOTOR_A.Encoder`，抄的位置在车型符号修正之后，所以速度环、OLED、`RosUp.vA`
  都不需要改；
- **前提**：B 的编码器必须接到 TIM3 的 PB4/PB5。没接的话左侧实测恒为 0，
  闭环会把左侧占空比顶满 —— 这比开环危险，台架第一步就要确认 B 有读数。

不想改固件也可以把 B 的编码器线直接插到 A 的编码器输入端（TIM2，PA15/PB3），
效果等价，然后把 `LEFT_ENCODER_IS_B` 改回 0。并联电机的速度差只来自负载差异，
环路按 B 控制，A 电机会跟随；代价是失去左侧两轮的独立诊断。

## 5. PID 实测（沿用 `tools/velocity_pid_tune.py`，在上位机侧）

1. 从 5800 / 820 起步，0.3 m/s 跑 3 次，看稳态误差、90% 上升时间、超调。
2. 上升慢 → 加 `KP`；有稳态误差 → 加 `KI`（先小步，`KI` 加太猛会振荡）。
3. 超调大 / 抖动 → 减 `KP`。改完必须重新下载固件或用 0x31/0x32 串口命令
   在线改（`usartx.c` 里 APP 参数通道，`Data` 是 u8，只适合粗调）。
4. 记录每次的参数和结果，写回 `system.c` 的注释里。

## 6. 已知上限与风险

- **最高车速下降**：70:1 在同一电压下轮速约为原来的 0.43 倍，95% 占空比大约
  只剩 **0.4 m/s 左右**。上位机的速度限幅（导航 / 遥控）必须降到 0.35 m/s 以下，
  否则速度环长期饱和，PID 再怎么调也没用。
- **编码器失效 = 满占空比**：闭环没有做"编码器长期不转"的检测。若要加保护，
  建议在 `Balance_task` 里做：输出饱和且实测速度接近 0 连续 N 拍（例如 50 拍）
  → `Incremental_PI_Reset()` + `MotorExt_Brake()` + 置故障位。本轮未实现。
- 轮胎直径、轮距、轴距本轮未改，`FourWheel_real_*` 仍是 2026-09 的实测值。
