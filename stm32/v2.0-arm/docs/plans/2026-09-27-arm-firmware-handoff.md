## 1. 固件端最终状态

已实现并验收的能力：

- 上电自锚：任意停车位置（全周期 ±160° 内）约 3.8 秒自动建立绝对角度并**自动回中到车头 0°±6°**；圈数正确性由任务尾回 0 纪律保证，异常停车（距车头 160°~450°）错圈为已接受残余（人工修复，见 §6）。**这条只管上电**——遥控器回位不走它，见下一条。
- **遥控器回位用累计角**（2026-09-28 改动，`_apply_arm_rehome_keep.py`）：跟踪器健康时回位**不重锚**，直接用累计角倒着绕回真车头 0°，行程不再限于半周期；只有底座角度未知（冷启动 / 底座故障）才重锚。见 §2.2、§8。

- 断链安全行为：指令 200ms 内归零、五关节保持上力、底座按惯性滑行（见坑 5.1）。
- 0xAD 透传（bring-up 遗产，可从主机直接驱动舵机总线原始帧）。

## 2. 主机看到的实测行为（协议注释之外的部分）

### 2.1 链路与保持

- 0xAA 保活帧 **12 字节**：AA 0C vx(2) vy(2) wz(2) flags seq crc。flags bit0=enable。
- **坑：0xAA 帧短 2 字节时完全没有报错。** 解码器 CRC 拒收、无任何反馈；且 `s_have_link` 初始为 0，看门狗不触发，**连 TIMEOUT fault 都不会置位**（fault=0x00 不代表链路好）。唯一症状：`RosDown.flags` 恒 0 → ArmHold 恒 1 → 底座/五关节全部不动。写帧后先用 0x55 上行帧的 fault 字节 + 0x56 的 ESTOP 位双重确认。
- ArmHold 五个条件：急停、链路超时、未使能、底座 FAULT、（EN 引脚 PD3 物理开关经 RosFault.ESTOP）。断链滑行期间 ESTOP 位会与底盘 EN 状态混合表现。
- 断链实测：指令 200ms 内归零、ESTOP 置位、五关节保持上力；**底座以断链瞬间速度滑行，实测 120°/s 滑行 ~185°、2.5 秒**。恢复链路后朝断链前目标**继续走**（目标持久语义，已接受）。

### 2.2 上电锚定与回中期（INIT_HOME）

- 复位姿态时长**按实际行程自适应**（300~2000ms，7ms/count）：五关节已停在复位姿态附近时快速微调，远端时温和长摆——固定 2s 会因舵机位置分辨率产生可见的一格格爬行。
- 锚定接受**任意主值读数**（全周期，无人工引导态）；byte19 恒 0（保留字段）。
- 锚定确认 = 150 次带内读数（~3.8s，与五关节复位并行）；期间底座保持上力。
- 读失败率 ~22%（50Hz 下周期性出现，与底盘上行帧同步），表现为 pot_raw=−1、五关节回读 0——**丢失是常态不是故障**，锚定计数对此免疫（miss 保持计数不重置）。
- 锚定后自动回中到车头 0°：命令速度带斜坡（40 档/拍，~300ms 匀加速），容差 6°、超时 12s 兜底放行。
- **INIT_HOME 也是遥控器回位的路径**（`ROS_ARM_FLAG_REHOME` 走 `INIT_POSE → INIT_HOME`），它分两条：
  - **底座角度已知**（`ArmBase.state == 2`，跟踪器健康）→ **不重锚**：`arm_base_init`（`arm.c` 的 INIT_POSE 交棒处）与那 150 拍锚定确认**都被跳过**，直接用累计的 `ArmBase.deg` 回中，**行程不再限于半周期**（12s 预算 ≈ 900°，远超现实 ≤360° 的行程）。`ARM_ST_BASE_KNOWN` 全程保持置位，`ARM_ST_HOMING` 在回中完成时清零。
  - **底座角度未知**（冷启动 / 底座故障）→ 走上面那套重锚流程，**这是唯一的恢复手段**，不可丢。
  - 上电**永远是**第二条（任务启动时 `ArmBase.state = ARM_BASE_UNKNOWN`）。判据无歧义：带着 `state == OK` 进 INIT_HOME 只有"回位"这一条来路，所以不需要新增状态量。
- 五关节回读的 0 语义 = "该拍没读到"，不是位置 0。
- 总线丢失连续 10s（舵机彻底不应答）→ 放弃底座（BFAULT、五关节照常），byte19 保持求援语义已废弃——主机看 base_st=0 + BFAULT 即可。

### 2.3 运行期

- 0x56 的 base_deg_f × 0.36 = 度（软限位 360 后的刻度）。
- 五关节回读每拍 2 个轮询，值偶发 0 同 2.2。
- 夹爪：机构实际行程 68~625，限幅 600；给 875 会停在机构极限（限幅生效）。
- 大步长点到位欠冲 ~3.4°（− 方向）、+ 方向可到 0（KP=18，摩擦停走所致，非 bug）。
- 速度标定非线性且方向不对称：+300 实测 244~295 raw/s，−300 实测 330 raw/s；+ 侧（车左方向）拖沓，接近 +160° 时显著。跟随若出现方向相关的跟随误差差，根源在此。

## 3. 电位器几何（所有底座角度问题的根源）

- 回绕周期 **320.3°**（1388 raw），边界对 raw −194/+1194，对称于中位 500。
- 中位 raw 499 = **车头 0°**；车左 90° = raw 889；**正角度 = 车左**。
- 主值范围 [−160.2°, +160.2°]；跨边界时读数跳变 ±1388 raw——这是回绕，不是故障。
- **坑：同一读数对应相差 320.3° 的两个物理位置。** 上电锚定接受任意主值读数，圈数正确性由**回 0 纪律**保证。**底座被停在距车头 160°~450° 时（断电手掰/异常甩停），上电会错一圈锚定**（部分情况静默）——已接受的残余风险，人工修复 = 把底座摆回车头重新上电。未来 flash 持久化（stmflash 现成）可消除。
- 运行期（已锚定后）没有这个限制：解包跟踪跨圈自由，±360° 任务范围内连续可信。
- **遥控器回位也不受这个限制**（2026-09-28 起，见 §8）：跟踪器健康时回位走累计角，不会就近错圈。**所以"错一圈"现在只剩两个入口：上电、以及底座已故障/未知之后的重锚。**

## 5. 坑册（现象 → 根因 → 现状）

### 5.1 时序与总线
1. **lx_read_pos 超时的 ready 清除竞争**（#15）：先发查询后清 ready，快应答的舵机在发送函数的 TC 等待 + 500µs 间隙内就把应答发布完毕，随即被入口清除抹掉 → 100% 超时。透传的 `lx_raw_exchange` 因"先清再发"从未触发。已修（清除移到发送前）。教训：**同一路径多个调用方时序不同，一个工作不能证明另一个工作。**
2. **50Hz 读数 ~20% 失败率**：半双工总线碰撞，LxRx 层表现为帧计数增长但 len 不匹配被丢弃。**丢失 ≠ 底座异常**，锚定与跟踪都已对此免疫；但任何"连续 N 次成功"式的判定都会被它饿死（曾导致锚定永不完成），要用"带内累加、丢失保持"。
3. **STOP 洪水**：无链路时运行块每 tick 对五关节发 5 帧 MOVE_STOP，会吞掉透传写入、冻结姿态动作。现被 INIT_READY 门控挡住（锚定期不运行）——**不要把控制段落移出门控，也不要在门控外新增对五关节的写**。
4. **lx_wait_reply 的入口清除不能恢复**：它必须不清 ready（早期应答），清 ready 只能发生在发送前。

### 5.2 电位器几何
5. 回绕跳变（±1388 raw）是正常现象；主值 [−160.2, +160.2]；跨边界由解包处理。
6. 别名：同一读数差 320.3°；**上电**且停车在 265~375.6° 时静默错圈（见 §3，已接受）。遥控器回位不再有此问题（§8）。
7. 电位器读数在任何模式下都回绕——**舵机自己的位置环也一样**（环绕误差 ≤±半周期，永远停在当前圈），切舵机模式回中解决不了圈数，且位置目标只有 0..1000、圈外位置无法指令。连续旋转必须电机模式。

### 5.3 机械
8. 夹爪真实行程 68~625（下限由用户手摆定位），限幅 600；ID4 小臂在 ~765 处是**力竭不是限位**（大臂伸展姿态负载所致），不设限幅。
9. 底座 + 方向（车左）摩擦拖沓：同指令速率差 ~35%，接近 +160° 时加剧。速度标定非线性（141@200 / 270-330@300 raw/s）。
10. 电机模式速度 0 = 自由滑行不锁轴；断链滑行由此而来（§2.1）。

### 5.4 环境与工具链
11. EMI 可让 Pi 的 USB hub 掉端口（内核日志 `disabled by hub (EMI?)`），适配器重枚举换编号；STM32 本体不受影响。整改建议：磁环、走线远离动力线。
12. mingw64 ld 不接受含中文的绝对路径（gcc 编译可过、链接失败，Python 侧表现为 stderr 解码异常）。中文路径下编译一律 cd 进目录用相对路径。
13. `_gen_servo_e2e.py` 已失效（引用的标记在 revert 后不存在），不要照抄。

### 5.5 已修复的固件缺陷（防回归）
14. **#13 姿态冻结**：INIT_POSE 后 2 tick 即进 READY，无链路时 STOP 洪水 20ms 内冻结复位动作。现被锚定等待 + 门控结构性修复——**不要缩短 ANCHOR_CONFIRM_TICKS 到 2s 以下**。
15. **#14 圈数别名**：本档 §§3 的全部来源。
16. **#15 ready 清除竞争**：见 5.1.1。
17. **#11 家族**：任何新加的断言先做变异验证（制造缺陷→确认变红→还原）；生成器里的断言（带宽公式、3a/3b/3c 顺序）都经历过这一步，改动它们时同规矩。

## 8. 2026-09-28：遥控器回位改用累计角

**现象**（用户报告）：遥控器 START 回位后，底座"和第一次上电一样找最近的"，转过一圈以上时会停在差一圈的位置。

**根因**（链路已实测确认）：遥控器 START（`ps2_teleop_node.py` 的 `BTN_REHOME=9`）→ `/arm/rehome` → `l150pro_driver_node.py` 发 0xAC `flags bit0=1` → 固件走 `INIT_POSE → INIT_HOME`，而 `INIT_HOME` 的锚定会把 `ArmBase.deg` **退回主值**（[-160.2°, +160.2°]），于是回中只走 ≤160° 的"就近"路。**回位和上电共用同一套重锚流程**，所以必然就近。运行期本来没这问题：`arm_track_step()` 每拍解缠，`deg` 是累计、跨圈连续的。

**改动**（`BALANCE/arm.c`，3 处，共 5 行行为；`_apply_arm_rehome_keep.py` 可复执行）：

| 位置 | 改动 |
|---|---|
| INIT_HOME 入边沿钩子 | 清 `ARM_ST_BASE_KNOWN\|ARM_ST_BASE_FAULT` 加守卫 `if(ArmBase.state != ARM_BASE_OK)` |
| INIT_POSE 交棒处 | `if(ArmBase.state != ARM_BASE_OK) arm_base_init(&ArmBase);` |
| 回中完成分支 | 补 `RosArmFb.status &= (u8)~ARM_ST_HOMING;`（keep 路径跳过锚定块，否则这位卡死） |

**"跳过重锚"是白送的**：`INIT_HOME` 的锚定块本来就是 `if(ArmBase.state != ARM_BASE_OK)`，只要估计活下来就自然被跳过，控制流直接落到回中段——而回中段本来就是 `arm_track_step` + `err = -ArmBase.deg`。**回中段一行未改。**

**刻意不改**：上电就近回中（用户确认保持）；五关节仍回 `ARM_RESET_POSE`（用户确认保持）；`ARM_CENTER_TIMEOUT_TICKS` 保持 600（12s 预算 ≈900° 行程，远超现实 ≤360°）；不新增任何舵机调用点；`arm.c:494-514` 那段死代码（锚定块的逐字副本，两条路径都 `break`，永不可达）保留。

**残余**：可表达范围仍是 ±360°（`arm_deg_to_field` 的钳位）。若回中**真超时**且残留 `|deg| > 360`，回中结束时写进 `ArmPos[base]` 的影子会饱和，运行期随后会朝偏差方向再走一段——需要 `|deg| ≳ 900`（超出 12s 预算）才可能触发，记为纸面残余。Pi 侧 `ps2_teleop_node.py` 的 `base_t` 钳位/残留问题**本次未动**（`on_fb` 的 1s 无输入窗口会自愈），验收用例 R4 覆盖。

**已验证（2026-09-28 实车，新固件已烧录）**：双宏值零诊断、宿主测试 39 项全绿；实车 R0/R1/R3 通过，判据见 `2026-09-27-acceptance-checklist.md` §R 的结果表。**决定性证据是行程**：旧路径数学上封顶 ±160.2°，而实测两次回位分别走了 **−342°**（+347.8° → +5.8°）和 **+235°**（−237.2° → −2.2°），落点都在 6° 容差内；回位期状态字 `0x0b`（`BASE_KNOWN` 保持）对旧固件的 `0x09`（被清）。**R2（底座故障后仍能重锚恢复）未测**——那两个守卫的假分支就是原代码逐字，`state != OK` 路径代码未变。**`byte19` 未验**（未走上行话题，读它要独占串口）。
