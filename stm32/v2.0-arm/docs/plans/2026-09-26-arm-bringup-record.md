## 2. 工具链修复（_ros_tooling/_arm_probe.py）

1. **`wrap_raw` 只检查 `buf[0]==0x57`** → 上行是 0x56/0x55 遥测交织流，0x57 永远不在缓冲区首位 → 所有查询超时（本次全部 `NO REPLY` 的根因；此前探针只做过宿主测试，从未吃过真实交织流——即 Self-Review #8 同类缺陷）。已改为全流扫描 + CRC 校验；正例/变异（改坏 CRC 必须拒收）/回归三项自检通过后部署。
2. **新增 `--keepalive`（10Hz 发 0xAA enable、零速）**。根因：无底盘链路时 `ArmHold` 恒真 → 运行块每 tick 对 5 个位置关节发 `lx_move_stop`（arm.c:816–828），既有 STOP 洪水又有回读，透传写入 20ms 内被掐掉。0x56 的 ESTOP 位确认解除。0xAA 用 `_TXLOCK` 与主线程写串行化（裸 write 与保活线程竞争曾导致全部帧失效）。
3. `cmd_id` 加 3 次重试（半双工总线上与固件回读碰撞约 30%）。

## 3. 事故与复盘

### 3.1 线缆缠绕（M1 电机版测试中）
- 经过：电机版 M1 累计单向转动 ~600°+；读数钉死在 1193 被误判为机械限位并继续顶了两次；实为线缆拽紧。spin 收尾会卸力，卸力状态下线缆扭转回弹把底座拽过中位（读数 −144）。
- 用户澄清：全程未手动转动底座；"第二次角度更大"即线缆缠绕。
- 处置：立即停转卸力 → 用户手动解线 → 松弛中位 raw 499 记录在案 → 之后所有底座标定改**手动**（零风险），M1 判定因此反而更干净。
- 教训：①转动预算要显式记账（±720° 是硬约束）；②回绕型上"读数钉死"可能是线缆/机械约束而非传感器轨道；③卸力 ≠ 安全静止，线缆储能会自己动。

### 3.2 EMI 导致 USB 掉线（M7 扫 ID4 时）
- 内核日志：`usb usb2-port2: disabled by hub (EMI?)` → 适配器重枚举为 **ttyACM1**（id 1a86:55d4，CH9102 "USB Single Serial" —— 即 STM32 经 USB-TTL 桥接 Pi，**STM32 本体未重启**，舵机保持/固件状态无任何中断）。
- `/dev/l150pro` udev 别名正确跟随重枚举 → ROS 驱动 Restart=always 可自愈。
- 整改建议：适配器加磁环、走线远离舵机动力线。

## 4. 固件缺陷（新增，未修复）

### #13 上电复位姿态被 STOP 洪水冻结
`INIT_POSE` 仅持续 1 个 tick（arm.c:490–497 发 5 帧 WAIT_WRITE + 广播 MOVE_START），下一 tick 即进 INIT_HOME；CAL=0 分支立即转 INIT_READY。无链路时 ArmHold 恒真 → 每 tick 5 帧 lx_move_stop 把 2000ms 的复位动作在 ~20ms 内掐死。**表现**：ROS 驱动停着时上电，关节冻在半路（冻结位随启动时机不同而不同，读数曾见 [106,98,307,105,250] 等数组）；驱动在跑时 ArmHold 解除、复位正常（用户最初看到的复位）。
**修复方向**：INIT_POSE 等动作完成（≥2000ms + 裕量）再推进；或 INIT 阶段豁免 STOP 洪水。

### #14 回绕分支无法建立绝对角度（已决策并执行：全周期锚定 + 回 0 纪律，见 §8/§8.9-10；下方会诊记录为历史）
周期 320.3°（= 1388 raw × 0.2308）< 包络 450°（±225°）→ 窗口内读数在 ±225° 上**不唯一**（相差恰一周期）。数值验证：停 +224° → raw 82 ∈ [40,1000] → 上电即误判 −96°。触发场景：①停在最外侧 ±(204.9–225)°；②停在任何负角度盲区（上电搜索方向固定为 −1，跨过 −160.2° 边界后进入别名区）。错一周期 = 固件持错 320° 闭环，首条指令即甩线。跳变标记只能锚定"±160.2° mod 320.3°"，无绝对参考时 k 不可知——物理限制，非实现错误。
另：T6 的回绕分支从未被植物模型测试（默认宏为截断分支，sim_pot 也是钉轨模型）——凡改 `ARM_POT_WRAPS` 必须同步改 `_arm_tests.c`：sim_pot 回绕化、direction 用例分支化（回绕的合同是"错提示仍可达+行程有界"而非"提示无关"）、死电位器 gate 400→500（REVERSE=1 双程腿）、窗口映射字面量更新。
**三个候选**（已呈报）：缩包络至 ±160° / 加 AS5600 / 操作纪律。
**2026-09-27 会诊结论**（用户追加硬约束：行程必须 ±225° 且不加磁编码器；已递话至设计会话 `7d83f1a1`）：这是**信息问题非算法问题**——θ mod P 永远分不出 θ 与 θ+P，机构无止挡，必须加一个**非模绝对参考**。推荐**方案 b：非磁索引开关**（微动开关+凸轮挡块，或槽型光电），装在 **θ≈0（中位）** 而非极限位——理由：①自解歧区内可与电位器交叉校验（开关闭合时读数最近同余候选必须落在 `ARM_HOME_SW_DEG±TAB/2`，否则判开关卡死→故障）；②不限行程、不磨损舵机；③上电常已闭合、寻零瞬间完成。**且回绕型+绝对锚点反而让固件变简**：BLIND 状态/速度积分/accel_comp/窗口探测/方向提示/有界搜索全部可删，运行时只做"把 raw 解到离估计最近的文章同余候选"；寻零换单一固定方向 + 470° 行程预算（超限=开关故障）。协议 0x56 第 19 字节 reserved→sw_state；探针加 `sw` 子命令；新常数 `ARM_POT_PERIOD_DEG/HOME_SW_DEG/HOME_SW_TAB_DEG/HOME_ANCHOR`。⚠️ 实现前必须做 **GPIO 空脚普查**（arm_task 50Hz 轮询即可，无需 EXTI；已知占用 PA7/PA8/PA9/10/PD5/6/PC6-9/PB14/15/TIM1/9/10/11/TIM2-5）。协议规范 §7.9 原文即写明"需要一个物理回零开关或人工复位流程"——软方案当年是因误判截断型而选的。(c) flash 持久化 θ 的改进版（限频写+上电一致性比对，不一致即故障）作为无硬件 fallback，但对方明确不推荐：它降低而非消除人工介入。遗留问题（待用户定）：先让设计会话出 Task 11 实现计划，还是先台面装开关量 `ARM_HOME_SW_DEG`。

### #15 lx_read_pos 的 ready 清除时序竞争（锚定失败根因，已修复待烧录验证）
**现象**：锚定循环 100% 读不到底座（byte19=1 不释放），但透传读同一舵机完全正常；诊断帧（pos[0]=LxRx 帧计数、pos[1]=错误计数、pot_raw=−1 区分读失败）显示：LxRx 以 ~79 帧/秒正常收帧（≈回声+应答各一）、错误 0、读超时——**应答到了、被抹了**。
**根因**：`LX_QUERY` 先 `lx_send_cmd` 后进 `lx_wait_reply`，而 `lx_wait_reply` 入口先 `LxRx.ready = 0`——快应答的舵机（电机模式的底座）在 `lx_send_frame` 的 TC 等待 + 500µs 间隙内就把整个应答帧发布完毕，随即被入口清除抹掉，之后干等 20ms 超时。位置模式的关节应答慢几拍恰好躲过窗口，所以旧固件的五轴回读从未暴露此 bug；透传的 `lx_raw_exchange` 是先清再发，顺序正确，所以一直正常。
**修复**：清除移到发送之前（LX_QUERY 内 `LxRx.ready = 0` 先于 `lx_send_cmd`），`lx_wait_reply` 不再入口清除——与 `lx_raw_exchange` 的已验证时序一致。
**教训**：①"先清标志再启动产生者"——清除发生在启动之后就会丢掉早期结果；②同一路径两个调用方（透传/直读）时序不同，一个工作不能证明另一个工作；③诊断帧（空闲字段发布计数器）一轮烧录就定位了纯硬件时序问题，是本次最有效的手段。
**#15 后续（第三轮烧录实测）**：竞争修复后仍不锚定——诊断帧显示读数成功率 ~80%（帧计数 79/s ≈ 回声+应答都在，errs=0），而锚定条件要求 **150 拍连续**成功：总线上 ~20% 的读数因碰撞丢失（与旧固件回读偶发 0 值一致），一次丢失即清零计数器 → 永远凑不满。**修正**：确认计数改为"带内读数累加，总线丢失保持计数不重置"，只有**真正读到带外值**（人动了底座的证据）才重置；另加 10 秒纯失败熔断（舵机完全不应答时放弃底座、五关节照常工作、byte19 保持 1 求援）——避免了死舵机把整条手臂堵在 INIT_HOME。确认语义从"连续 N 拍"修正为"N 次带内读数（容忍碰撞丢失）"，是对复审条款的实现层修正。

### #16 锚定等待期的卸载洪水（第六轮现场排障）
**现象**：全周期锚定版本烧录后，锚定循环读数 100% 失败（pot_raw=−1 持续），而透传直读同一舵机正常（483）。
**根因**：miss 分支每拍发一帧 `lx_torque(6,0)`（round-5 人工引导路径的遗留物——那时卸载是为了让人能转底座）。50Hz 的卸载帧 + 查询帧 + 回声把舵机应答全部淹没 → 读失败 → 又发卸载 → 自激死循环。透传读取带 3 次重试 + 60ms 收集窗，能在洪水中活下来，掩盖了问题的严重性。
**修复**：round-6 已删除人工引导路径，miss 分支**不发送任何帧**（只计数与发布 pot_raw=−1）。
**教训**：①状态机分支里的"每拍无条件写"在语义演进后必须重审——人工引导被删除后，它的卸载帧变成了毒药；②诊断帧（计数器增量）+ 透传对照，一轮烧录定位；③"重试能活下来"的读取路径掩盖了单发路径的脆弱性。

### #17 未锚定 miss 分支清零确认计数 + 总线 ~22% 读失败的既存性（第七轮诊断实测）
**现象**：#16 修复（miss 分支零帧化）后读数仍间歇失败——诊断流显示：帧计数 70+/s 稳定、errs=0、last_len=8、last_id=6（应答格式完全正常），**失败率 22%、且全部以"连续 2 拍"的运行长度出现**，周期与 50Hz 底盘上行帧（28 字节阻塞式 TX ~2.4ms）吻合。
**根因两层**：① ~22% 的读失败是**自古以来就存在的总线条件**（疑似与底盘 0x55 上行的阻塞发送相关，未深究）——旧固件的五轴回读同样间歇出 0（"0 = 没读到"语义就是在容忍它），**不是新 bug**；② 我的锚定确认要求"连续 150 拍成功"，而未锚定态的 miss 分支把 `anchor_ok` 清零——22% 失败率下 0.78^150 ≈ 0，**永远锚不上**。与 #15b 同族：把"总线丢失"当成了"位置被移动"的证据。
**修复**：确认计数改为**带内读数累加、miss 保持不重置**（仅有 `anchor_miss > 500` 连续纯失败熔断，且熔断计数也在成功读数时清零）。诊断帧暂时保留（pos[0..2]），锚定验证通过后删除。
**教训**：①间歇性失败的"运行长度分布"是最有信息量的诊断数据（全 2 = 周期性干扰，不是随机碰撞）；②容忍性判据必须覆盖真实环境的基线失败率，"连续 N 次成功"在 N 大、基线失败率高时等于永不通过。

## 8. 360° 跟随扩展的设计结论（2026-09-27）

工作场景：抓取面前物体放背后平台（~180° 摆动）+ 360° 跟随（用户确认超限风险自担）。用户方案：任务编排层保证**任务尾强制回 0**，上电即停车头附近 → 现有安全带锚定天然正确，**不需要换舵机模式**。

设计结论：
1. **正常运行（已锚定）无圈数误差**：解包跟踪让估计连续贴着真值走，任意圈数任意距离；360° 跟随的固件障碍只有一个——目标软限位钳制 ±225°，跟随开工时 `ARM_SOFT_LIMIT_DEG` 225→360（一个常数 + 主机侧知道新的 field 刻度 0.36°/count）。
2. **异常结束的残余风险（用户接受）**：异常停在距车头 265°~375.6° 弧段时，主值落回带内 → 上电静默错一圈。表现是"软"的：第一次回 0 指令后底座肉眼可见地不在正前方 → 人工修复 = 底座摆到车头位置重新上电（重新锚定）。系统不会主动提醒这一种，flash 持久化（stmflash 现成）是未来的可选保险，用户决定暂不做。
3. **位置模式不能替代电机模式做无限旋转**（架构级，三重原因）：①位置目标只有 0..1000 编码，raw <0 / >1000 的物理位置位置模式无法指令也无法保持；②舵机内部位置环的误差按最短环绕计算（≤±半周期），永远停在**当前圈**第一个误差零点，不会跨圈追目标；③角度限位寄存器本身 0..1000 编码。连续旋转必须电机模式——厂家提供电机模式正是为此，现行分工（底座电机模式 / 五关节位置模式）是架构正确的。
4. **主机侧约定**：0xAC 的 base 目标必须用**连续角度**表达（跨圈时不 mod 320.3，否则速度环会绕远路）；field 刻度随软限位常数变化。
5. 任务尾回 0 由 ROS 编排层发；建议抓放每轮结束、跟随退出时各回一次 0（缩小异常暴露窗口）。
6. **最终轮常量（已入源码并烧录）**：`ARM_SOFT_LIMIT_DEG` 225→**360**（field 刻度变为 **0.36°/count**，usartx.h 注释已同步）；`ARM_VEL_KP` 10→**18**；锚定诊断帧已删（`pos[]` 恢复纯回读语义）；usartx.h pot_raw 注释补充 **−1 = 锚定期读数失败** 哨兵语义。验收驱动 `~/acc_driver.py` 的 field 换算已同步 360 刻度。
7. **主机侧对接契约（写其他端时必读，第六轮修订）**：① 0xAC base 目标用**连续角度**（跨圈不 mod），field=deg×1000/360；② 0x56 的 base_deg_f × 0.36 = 度；③ **byte19 恒 0**（全周期锚定后无人工引导态，字段保留）；④ pot_raw=−1 = 该拍读数失败（保持上次值即可）；⑤ 链路保活 = 25Hz 0xAA（flags bit0=1），断 200ms 进保持。
8. **第五轮（上电回中）**：锚定确认后、放行控制环前，固件以同款速度环把底座驱动到车头 0°（容差 4° ≥ 摩擦停走残差 3.4°；超时 12s 兜底放行）。行程上界 = 安全带半宽 55.3°，全程在无歧义区内。锚定期的读失败分支与回中期的读失败分支分开处理（前者卸力喊人，后者保持现速等重读）。常量 `ARM_CENTER_TOL_DEG=4.0 / ARM_CENTER_TIMEOUT_TICKS=600`。B1 验收判据随之更新。
9. **第六轮（全周期锚定，用户决策）**：用户拍板放弃 55.3° 安全带——"功能层保证回 0 后，安全区就是电位器能读到的 320.3°"。实现：`arm_boot_anchor` 与安全带常数（ENVELOPE/NOISE/BAND）整体删除；锚定接受**任意主值读数**（上电第一拍），回中行程上限变为**半周期 160.15°**；容差 `ARM_CENTER_TOL_DEG` 4→**6**（−方向实测摩擦停走残差 5.4°@新刻度）。**代价（用户已接受）**：断电状态被手掰/异常停在距车头 160°~450° 的位置时，上电会错一圈锚定（部分情况静默）——人工修复 = 底座摆到车头重新上电。此前的带宽公式、生成器带宽断言、test_boot_anchor 同步删除。**更正**：第四轮验证报告中 "+225.0/−3.4°" 是旧刻度（0.225）误标，实际为 **+360.0° / −5.4°**。
10. **第七轮（回中斜坡）**：用户实测"底盘突然归 0"——回中指令是阶跃（arm_base_vel 大误差下直接顶到 VEL_MAX 钳制，无加速过程）。修复：命令速度加**每拍限幅斜坡** `ARM_CENTER_RAMP_STEP=40`（0→600 约 300ms 匀加速），末端随误差自然减速。减速自然、无额外逻辑。
11. **第八轮（自适应复位时长）**：用户实测五关节复位"一卡一卡"。根因：复位指令是一条 2s 连续插值，但关节常已停在复位姿态附近——几个计数摊 2 秒 = 舵机按位置分辨率一格格爬。修复：INIT_POSE 先读五关节当前位置，按最远行程自适应时长 `t = clamp(dmax×7ms, 300, 2000)`（读失败保守 ≥1s）；锚定确认 150 拍仍覆盖上限 2s，#13 保护不变。用户假设"固定 2s + 距离近 = 分段爬行"基本正确，机制修正为舵机位置分辨率所致（非固件分段）。
